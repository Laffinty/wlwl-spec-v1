### 2.4 交付包没有发现的三处规范侧缺口

#### 缺口 α:CI 的上游基线已过期 34 个提交 ⇒ 第 7 项对 v1.0 语义**没有鉴别力**(已核实)

`.github/workflows/spec-check.yml` 钉的上游是 `46b153b`(2026-10-22)。而 §5.4 那 13 条收敛
(X-01 / X-06 / X-07 / X-16…X-24)**发生在 2026-10-23**,随 **v0.11.4** 发布
(上游 CHANGELOG 的 `0.11.4` 段逐条记载了它们)。GitHub compare API:`46b153b...v0.11.4` ⇒ `ahead_by: 34`。

⇒ **CI 跑的是没有这 13 条收敛的旧实现** ⇒ §6.1 第 7 项对这些行为**判不了对错**。

⚠ **更糟的一层(推断,须证实)**:语言核心册 §8.6.3 的示例(**引自** `docs/spec/wlwl-v1.0-language.md`,此处**故意**不标 `wlwl` 围栏 ——
它是**被引用的失败样例**,不是可运行示例):

```
LET(a, [ERR("boom")]);
PRINT(a);        // 成员的结果(Null)承担那份未消费状态 ⇒ 本语句即语句值丢弃点 ⇒ 报 E0103
0
```

在 **v0.11.4** 上**退出码 1**(报 `E0103`,实测);而在 **46b153b** 上大概率**退出码 0**
(X-20 的收敛晚于该基线)。⇒ **CI 判绿,而块里的注释「报 E0103」是假的** ⇒
这正是 §6.4 说的最严重缺陷类型:「把没报错写成检查通过」。

**证实命令**(需要能构建上游 Rust 工作区):
```bash
git clone https://github.com/Laffinty/wlwl && cd wlwl && git checkout 46b153b
cd impl && cargo build --release && cd ..
printf 'LET(a, [ERR("boom")]);\nPRINT(a);\n0\n' > /tmp/x20.wll
./impl/target/release/wlwl run /tmp/x20.wll ; echo "exit=$?"
```

#### 缺口 β:§6.1 第 7 项缺「预期失败」的表达方式(已核实)

`script/check_spec.py` 第 7 项把「示例有效性」硬编码成**退出码必须为 0**
(第 13 行注释 + `check_samples()` 的 `if r.returncode != 0:`)。
⇒ **一个故意演示诊断的规范示例无法成文** —— 它必然判错。

而 §8.6.3 那个示例**必须**存在(它是 X-20 裁决的规范锚点),且它**故意**失败。

⇒ 规范需要一种表达方式:「这个块**预期**报 `E0103`」,且检查器要**断言实际诊断码与注解一致**,
不能只看退出码非零(否则任何错都能过)。

#### 缺口 γ:规范版本号轴与实现版本号轴被混用了(已核实)

一致性册 §3.2 明写:「**次版本**(`1.0.0` → `1.1.0`):新增能力(新章、**新成员**、新诊断码)且不破坏既有合规程序时递增」
「**修订版本**(`1.0.0` → `1.0.1`):只改措辞、修正笔误、补充解释性说明与示例时递增」。

⇒ **v0.13.0 要落地 17 个新公共面成员** ⇒ 对应的规范版本**必须**是 **v1.1.0**;
**v1.0.2 只能承载措辞/勘误/解释性说明/示例类改动**。
⇒ 「实现仓 v0.12.0 ↔ 规则仓 v1.0.2」这个配对**在规范自己的版本规则下不成立**。见 §3.1。

## 3 裁决

### 3.1 规范版本轴:v1.0.2 做登记,v1.1.0 做成员(已裁决)

**建议(单一方案,不是菜单)**:

| 规范版本 | 内容 | 合法性依据 |
|---|---|---|
| **v1.0.2** | §5.4 的 13 行状态订正 + 每行最小复现 + 状态列门禁 + §5.5 实现侧扩展台账 + §3.5.1 闸门扩写 + CI 基线前移 + §6.1 第 7 项「预期失败」表达方式 + §5.4 新登记 X-25 | §3.2:全部是措辞/解释性说明/示例/登记维护;**不动任何公共面成员** |
| **v1.1.0** | 17 个新成员进附录 A + 各标准库册成员表 + 传输层新章 + §8.3 消费者注册表增 `TAKE_ERR` + §8.6.2 第 3 项切段路径漏检 + 并发册「宿主挂起」 | §3.2:新增成员 ⇒ 次版本 |

**为什么必须分两段**:v1.1.0 的发布前置条件(§3.5 第 1 条)要求 §0.9 的「实现状态」列**没有**「未实现」或「部分」,
即**规范不能先于实现发布**。所以顺序是:规范文本先写(v1.1.0 草案)→ 实现落地(v0.13.0)→ 验证 → 发布。
而 **v1.0.2 是 v0.13.0 的前置**,因为实现侧那道新门禁要读规范仓的 §5.4:
**13 行不翻,实现仓一接门禁就是 13 条红**(交付包已实测:跑冻结规范 13 红、跑翻过的副本 24 全绿)。

### 3.2 实现版本轴:不要用 v0.12.0(已裁决)

**事实**(GitHub API,2026-10-25 实测):上游 `Laffinty/wlwl` 的 tag 与 release 列表里
**没有 `v0.12.0`** —— 最新已发布是 `v0.11.4`(2026-10-24)。上游 CHANGELOG 自己写:

> ⚠ **`v0.12.0` 不是既定发布点** —— 该 tag 系**先前 agent 私自打出、未经业主同意**;
> 版本线上以 **`v0.11.4` 为准**。

且上游 CHANGELOG 里**至今保留**一段 `## [v0.12.0] — 2026-10-22(正式版)`,内容是 E0103 批次那批改动。

⇒ **v0.12.0 是一个已被用过、又已撤回、且在 CHANGELOG 里留有历史段的号**。本批再用它,
同一个文件里会出现两个 `v0.12.0` 段(内容完全不同)⇒ 读者与工具都无法判断哪段是本次发布。

**建议:实现侧本批发 `v0.13.0`**。理由三条:

1. **高于任何已发布版本**(v0.11.4)且**高于历史里的 v0.12.0** ⇒ 不回退、不撞号;
2. 本批**含 breaking**(`std.fs` 的 IO 失败从原生诊断改为 `ERR` 值 ⇒ 依赖 `E0062` 诊断的程序行为改变),
   按上游 ADR-0023 §v0.x 2「0.x 内 breaking 升次版本号」⇒ **次版本号** ⇒ v0.13.0 正是次版本;
3. 上游 `impl/Cargo.toml` 有硬规则:「**发 vN.M.P 之前先把这个数改成 N.M.P**」,
   且 `[workspace.dependencies]` 里 10 条 path 依赖的 `version` **必须一起改**(漏改会在下次 `cargo build` 直接炸)。
   ⇒ 版本号这件事在实现仓是**机器守卫**出来的,不是文字约定。

⚠ 若业主要坚持用 v0.12.0,则**必须**先把上游 CHANGELOG 里那段 `[v0.12.0] — 2026-10-22(正式版)`
改标成「未发布的历史痕迹」,否则仓内会出现两个 v0.12.0 段。**这一条我没有替你决定 —— 见 §8。**

### 3.3 公共面扩展的登记路径:甲 + 乙 分工(已裁决)

交付包把这道题做成二选一(**甲** = 一致性册增设「实现侧扩展台账」;**乙** = 走规范修订流程)。
**二选一会留下一个永久红灯**,分析如下:

- **只选甲**:台账里的成员**不是规范公共面** ⇒ 实现侧「实现成员集合 == 附录 A 集合」的门禁**永远红**
  (交付包自己说这 8 个 target / 9 条用例是「刻意保留的预期红」)⇒ 红灯久了就没人看
  ⇒ §0.7 规则 1 明禁的「偷偷改快照」就会重新长出来。**缺口被藏起来。**
- **只选乙**:实现侧在规范修订完成前加的任何成员**无处登记** ⇒ 门禁红 ⇒ 开发者只能去改附录 A
  ⇒ 而附录 A 是**冻结快照**,§0.7 规则 1 明写「表体**不得**为追平实现的当次改动而改写」⇒ **规范被污染。**

**建议(分工,不是二选一)**:

| 场景 | 路径 | 落点 |
|---|---|---|
| 该成员**将成为规范公共面**(v0.13.0 的 17 个) | **乙** | 走 v1.1.0 修订:附录 A 重新冻结 + 各册成员表同步 ⇒ 实现侧门禁**绿** |
