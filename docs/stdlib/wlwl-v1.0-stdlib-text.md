## 0 导言与总则

### 0.1 本册的构成

本册定义 WLWL 标准库的**文本处理**部分:`std.text`(§12,Unicode 大小写、规范规范化与文本解析)、`std.sanitize`(§13,输出安全)、`std.regex`(§16,线性时间正则)。每章对应一个命名空间,每章含成员表(签名 / 语义 / 失败 / 复杂度 / 层)、共享失败口径、值形状与边界、示例与该章特有条款;附录 A 是**规范性**的成员注册镜像,由[标准库·注册镜像册](wlwl-v1.0-stdlib-registry.md)承载。

**成员数以附录 A 镜像为准**:本册各章的成员表与附录 A **逐项对拍**,两者**必须**集合相等。

全局内建(`PRINT` / `LEN` / `FORMAT` 等)**不在**本册重复定义,见语言核心册 §10.2–§10.5、§10.7、§10.9、§10.12 与其附录 G。

### 0.2 读者

本册面向三类读者:使用标准库的 WLWL 程序员、标准库实现者,以及需要判断某个成员行为是否合规的工具作者。

### 0.3 规范性用语

本册中的关键词 **必须**(MUST)、**不得**(MUST NOT)、**应当**(SHOULD)、**可以**(MAY)按以下含义使用:

- **必须 / 不得**:实现的硬性约束。违反时实现必须产生一个诊断(语言核心册 §11)并按 §11.4 终止或报告。
- **应当**:强烈推荐的行为;实现可以偏离,但偏离必须在本册或实现文档中说明。
- **可以**:真正的实现自由度。

标注为**非规范**(non-normative)的段落、注释与附录不构成一致性要求。

### 0.4 一致性

一个 WLWL 程序是符合本规范的,当且仅当它只使用本册定义的成员面,并按各章的语义与失败口径使用它们。一个实现是一致的,当且仅当它提供本册各章列出的全部成员,对每个成员给出规定的签名、语义、失败行为与边界,且不依赖任何标注为未定义、保留或实现定义的行为。

### 0.5 记法

成员表统一为**五**列:

| 列 | 含义 |
|---|---|
| 签名 | 成员名与形参;`?` 表示可选形参;`...` 表示变参 |
| 语义 | 正常路径的可观察行为 |
| 失败 | 失败时的可观察行为;`—` 表示**不因输入内容失败**。实参层诊断(元数错 `E0022`、类型错 `E0030`)适用于**全部**成员,由语言核心册 §8 与 §11.2 统一规定;各章**可以**重复列出以便查阅 |
| 复杂度 | 时间代价上界,记法见语言核心册 §18;`—` 表示规范不约束 |
| 层 | 实现分层(§0.7);R0 内建层 / R1 语言层 / R2 原生层 |

正文中的 `code` 样式表示词法记号、字面代码或诊断码。示例代码以 `//` 注释标出其求值结果。值形状用 `json` 标记的代码块给出。

**标点约定**:逗号 `,`、冒号 `:`、分号 `;`、圆括号 `()`、方括号 `[]` 一律用**半角**;句号 `。`、顿号 `、`、引号 `「」`、破折号 `——` 用**全角**。

**围栏约定**:文法块用**无标记**围栏;示例代码块用 **`wlwl`** 标记的围栏,且**必须**能在参考实现上运行且退出码为 0。

**失败示例的记法**:预期产生诊断的片段**不**写成 `wlwl` 围栏 —— 它们以非零退出码终止,不是可运行示例。本册用表格列出失败形态与预期诊断码。

**引用**:同册内写 `(§5.2)`;跨册写册名加节号,例:"语言核心册 §8.2"、"并发册 §17.3"、"一致性册 §3"。

**规范性标注**:本册**全部**为**规范性**;各章的「设计依据」小节是**非规范性**的追溯材料,不构成要求。

### 0.6 调用面

标准库的调用面只有两种形式,与实现层无关:

- **全局内建**(R0 内建层):无须导入;契约见语言核心册 §10.2–§10.5、§10.7、§10.9、§10.12 与其附录 G。本册不重复、不镜像全局内建。
- **命名空间成员**:`IMPORT("wlwl:std.X", [names])` 导入后调用;成员契约见本册各章。官方包 `ai` / `agent` 的导入路径分别是 `ai:ask` 与 `agent:task`。

**本语言没有「命名空间限定调用」表达式**:文法里没有 `ns.MEMBER(...)` 这种形式,冒号只出现在 `IMPORT` 的路径字符串与改名处。成员只能经 `IMPORT` 取裸名;需要避开与类型名同名时,在 `IMPORT` 时改名。

### 0.7 实现分层

| 层 | 实现语言 | 内容 |
|---|---|---|
| R0 内建层 | 纯 Rust(编译器/运行时内部) | 语言自身无法表达或与编译器强耦合的原语;即语言核心册附录 G 全部条目 |
| R1 语言层 | 纯 wlwl(`.wll` 源码,`include_str!` 嵌入二进制) | 不触系统调用且非性能敏感的库;**非敏感库的默认归宿** |
| R2 原生层 | 纯 Rust(`wlwl-std`) | 触系统调用、性能敏感、或需复用成熟 Rust crate 的库 |

**归属判定**(机械执行):

1. 触系统调用 / OS 资源 / 进程·网络·时间·随机 → R2;
2. 语言核心语义 → R0;
3. 其余 → R1;仅当基准数据证明热点且解释器短期无优化空间时下沉 R2;
4. R2 成员**必须**有不依赖实现细节的语义描述,保证可被 R1 等价替换。

**层间规则**:R1 **可以**调用 R0 与 R2;R2 **不得**调用 R1(确需时走白名单并登记偏差)。混合模块以门面(R1 侧)为对外契约层。层归属变更(下沉/上浮)**不算**破坏性变更,但**必须**附基准数据并登记。

**R0 / R1 / R2 是实现分层,不是规范层级。** 成员的规范强度与它落在哪一层**无关** —— 一个 R1 成员与一个 R2 成员承担同样的规范性义务(总纲 §0.6 规则 1)。

### 0.8 与语言规范的依赖与差异登记

本册以语言核心册 的值域、错误模型、模块机制、诊断码表、并发语义、复杂度保证与内存模型为前提,不重复定义。两册冲突时**以语言核心册为准**。

本册**唯一**的跨册差异登记是:`ERR` 的产生与消费规则。语言核心册 §8.6 规定"未消费的 `ERR` **不得**被丢弃",本册各章的「失败」列**只**描述成员自身在失败时**返回什么**,**不**复述 §8.6 —— `ERR` 值的丢弃与报告一律由 §8.6 承担。

## 12 `std.text` —— Unicode 大小写、规范规范化与文本解析

全局内建 `UPPER` / `LOWER` 只做 ASCII 映射(语言核心册 §10.5):非 ASCII 字符原样穿过,且不产生任何诊断。本命名空间提供**完整 Unicode 大小写映射**与**规范形式**(`NFC` / `NFD`);另提供 `TO_INT` —— 面向**外部输入**的**宽松**文本 → 整数解析(与全局内建 `INT` 的**严格**口径分工见 §12.4)。

本命名空间与全局内建**并存**,标准库**不替换**全局内建 —— 替换是破坏性变更(既有程序里非 ASCII 字符的大小写行为会变)。调用方按需要显式选:`UPPER` 快且只管 ASCII,`TO_UPPER` 全 Unicode。

本章的 Unicode 数据与切分口径以 **UCD 18.0.0** 与 **UAX #29** 为准;参考实现是 `Laffinty/wlwl`(基线提交 `99041ef`,见本册 §0 的「上游基线」行)。

| 签名 | 语义 | 失败 | 复杂度 | 层 |
|---|---|---|---|---|
| `TO_UPPER(s) -> STRING` | 完整 Unicode 大写映射;**长度可能变**(`ß` → `SS`) | — | O(n) 最坏 | R2 |
| `TO_LOWER(s) -> STRING` | 完整 Unicode 小写映射;希腊 `Σ` 词尾得 `ς`、词中得 `σ` | — | O(n) 最坏 | R2 |
| `NFC(s) -> STRING` | 规范组合:`"e"` + U+0301 → `"é"`,**长度变短** | — | O(n) 最坏 | R2 |
| `NFD(s) -> STRING` | 规范分解:`"é"` → `"e"` + U+0301,**长度变长** | — | O(n) 最坏 | R2 |
| `NFC_QC(s) -> BOOLEAN` | 规范快速检查(单方向语义见 §12.2) | — | O(n) 最坏 | R2 |
| `GRAPHEME_COUNT(s) -> INTEGER` | 字素簇数(UAX #29 扩展字素簇);**空串是 `0`** | — | O(n) 最坏 | R2 |
| `WIDTH(s) -> INTEGER` | 终端显示宽度(列数),**簇折叠**(口径见 §12.3) | — | O(n) 最坏 | R2 |
| `TO_INT(s) -> INTEGER` | **宽松**的文本 → 整数解析(**空白裁剪** / **十六进制文本** / **小数截断**,口径见 §12.4) | `ERR([kind: "ParseError", input, reason])`(**值**,**不是**诊断) | O(n) 最坏 | R2 |

**共享失败口径**:本章的失败分两类,**不得**混为一谈。

1. **内容级失败**(`ERR` 值):**只有 `TO_INT`** 会因输入内容失败 —— 解析失败时它返回 `ERR([kind: "ParseError", input, reason])` **值**(**不是**诊断),程序**不**因此中止;调用方按语言核心册 §8.3 的 `IS_ERR` / `ERR_PAYLOAD` / `UNWRAP_OR` 分支处理该 `ERR`(口径见 §12.4)。其余成员(`TO_UPPER` / `TO_LOWER` / `NFC` / `NFD` / `NFC_QC` / `GRAPHEME_COUNT` / `WIDTH`)**永不因内容失败** —— 对任意 `STRING` 实参,结果确定,不产生 `ERR`;成员表的「失败」列记 `—`,含义即此。
2. **实参层诊断**(程序员错误):实参不是 `STRING` 或元数不符时,实现**必须**按语言核心册 §11.2 报类型错 `E0030` / 元数错 `E0022`;这类诊断与输入内容无关,**全部**成员(含 `TO_INT`)一律如此。

**复杂度口径**:本表 `n` 是字符串的码点数(语言核心册 §18.1)。`TO_UPPER` / `TO_LOWER` / `NFC` / `NFD` 的输出长度与输入长度成常数倍关系(Unicode 大小写与规范分解的每码点展开有界),不改变阶。`TO_INT` 的代价是 O(n) 最坏(裁剪与解析各一趟)。

**值形状与边界**:

- `TO_UPPER` / `TO_LOWER` 的映射是**完整**的,含特殊映射:`ß` → `SS`、希腊 final sigma、土耳其无点 `i` / 点上 `i`。`TO_LOWER` 的希腊 `Σ` 取值**依赖词形位置** —— 词尾得 `ς`,词中得 `σ`。
- `NFC` / `NFD` **改变字符串长度**。任何以 `LEN` / `INDEX_OF` 的下标作为缓存键、行号或切分依据的调用方,规范化之后**下标全部失效**。
- **坐标系有两个,不可混用**:`LEN` 给**码点数**,`GRAPHEME_COUNT` 给**字素簇数**。`"👨‍👩‍👧"` 的 `LEN` 是 `5`,`GRAPHEME_COUNT` 是 `1`。
- 空串:`GRAPHEME_COUNT("")` 与 `WIDTH("")` 都是 `0`。
- `TO_INT` 的失败载荷是**字典**,三个字段:`kind` = `"ParseError"`、`input` = **原始**实参字符串(裁剪前的原串)、`reason` = 失败原因文本(其措辞**不由**本规范冻结)。
- **本章不覆盖**:兼容性分解(`NFKC` / `NFKD`)、case folding、locale 相关排序 / 比较。兼容性分解是**另一个语义** —— 它会把全角 / 半角、`①` / `1` 折叠掉,不能与 NFC 混在一处默认;case folding 是等价类判定,与 `TO_UPPER` / `TO_LOWER` 的映射不是一回事。

### 12.1 数据源与版本

本章的规范化与字素成员**必须**基于同一版本的 Unicode Character Database 实现 —— 本版固定为 **UCD 18.0.0**。数据依赖如下:

| 成员 | 依赖的数据表 |
|---|---|
| `NFC` / `NFD` | `UnicodeData`(规范分解)+ `CompositionExclusions` |
| `GRAPHEME_COUNT` | `GraphemeBreakProperty` + `Extended_Pictographic` |
| `WIDTH` | `EastAsianWidth` |

**数据覆盖必须完整**:实现**不得**只覆盖部分码位范围(例如只覆盖 Latin-1)而声称提供 `NFC` / `NFD` / `GRAPHEME_COUNT` / `WIDTH`。部分覆盖比不提供更危险 —— 它会让 `==(NFC(a), NFC(b))` 在部分输入上返回 `TRUE`,调用方据此建索引,然后在真正的 CJK 或组合字符上失效。

**正确性只由全量自检证明**:`GRAPHEME_COUNT` **必须**经官方 `GraphemeBreakTest.txt` 的全部 853 行自检,`WIDTH` **必须**经 `EastAsianWidth.txt` 的全部 1 114 112 个码点逐条比对。**部分自检不构成符合本规范的实现**。

**说明**:换 Unicode 版本**必须**同时更新生成产物与自检结果 —— 两件事一起做。只做其一会造成数据与自检的版本错位,而错位的自检结果是绿灯,比没有自检更危险。

### 12.2 `NFC_QC` 的单方向语义

`NFC_QC(s)` 返回 `TRUE` **当且仅当**该串**必定**已是 NFC 形态 —— 此时调用方**可以**安全跳过 `NFC`。返回 `FALSE` **只**表示「不保证」:该串**可能**已经是 NFC 形态。

**反向不成立,这是规范条款而不是实现瑕疵。** 官方测试数据中有 202 行的串本来就是 NFC 形态(`Maybe` 类单码点行,例如单独一个 U+0301 —— 它经 `NFC` 之后原样不动,却仍然有 `NFC_QC = Maybe`),快检一律返回 `FALSE`。

**本规范的文面不得**写成「返回 `FALSE` 即表示不是 NFC 形态」—— 那会教调用方一个假事实,进而写出「不是 NFC 就去 `TO_UPPER`」这类错误推理。

### 12.3 字素簇计数与宽度的坐标系

`GRAPHEME_COUNT` 按 **UAX #29 扩展字素簇**切分(Unicode **18.0.0**,含 15.1 新增的 **GB9.3** Indic conjunct break)。

`WIDTH` 是**簇感知**的:切簇后**每簇取簇内码点列宽的最大值**再求和。六条口径:

| 判据 | 列宽 |
|---|---|
| `EAW` = `W` / `F` | **2** |
| `EAW` = `A`(Ambiguous) | **1** |
| `EAW` = `N` / `Na` / `H`,**且**默认 emoji 呈现 | **2** |
| 一般类别 `Mn` / `Me` / `Cf` | **0** |
| 一般类别 `Mc` | **1** |
| 其余 | **1** |

**说明**:`EAW` = `A`(Ambiguous)取 **1** 的理由是 Unicode 自己把它定位为「西方 1 列、东亚 2 列」,而 `unicode-width` / `wcwidth` / `runewidth` 一律默认窄、CJK 是显式 opt-in —— 该类占全表 38.9%。`EAW` = `N` / `Na` / `H` **且**默认 emoji 呈现取 **2** 的理由是实测只影响 26 个码点,全是 U+1F1E6–1F1FF 区域指示符。一般类别 `Mn` / `Me` / `Cf` 取 **0** 的理由是零宽:`Cf` 含 U+200B / U+200D / U+2060 / U+FEFF,按 EAW 它们各得 1,会让每个零宽字符**占一整列**。一般类别 `Mc` 取 **1**(不置 0)的理由是带间距的组合记号(天城文 visarga 等)在真实字体里占宽度,`wcwidth` 同款。

**`WIDTH` 不做任何规范化折叠。** U+2122 OHM SIGN 与 U+00A5 YEN SIGN 是同一字符,本成员下两者都恰好得 1 —— 但那是**各自独立查表**的结果,**不是**识别出了等价关系。要按等价比较,先用 `NFC`。

### 12.4 `TO_INT` 的宽松解析口径

`TO_INT(s: STRING) -> INTEGER` 是本章**唯一**的数值解析成员,也是本章**唯一**会因输入内容失败的成员(失败口径见本节末与本章「共享失败口径」)。

**接受的形态**:它是**宽松解析** —— 除下述三条放宽外,十进制写法按语言核心册 §10.3.1 的规则。

| 形态 | 规则 | 读数 |
|---|---|---|
| **空白裁剪** | 解析前裁掉首尾空白;裁剪**只**作用于首尾,串内部的空白使解析失败 | `TO_INT("  42  ")` = `42` |
| **十六进制文本** | 接受 `0x` / `0X` 前缀的十六进制整数,十六进制数字大小写不敏感 | `TO_INT("0x1F")` = `31` |
| **小数截断** | 含小数点的文本**向零截断**为整数,小数部分被丢掉,**不**报「不是整数」 | `TO_INT("3.9")` = `3`;`TO_INT("-3.9")` = `-3` |

前导符号 `+` / `-` **至多一个**,符号之后**必须**紧跟数字(`TO_INT("-5")` = `-5`,`TO_INT("+5")` = `5`);结果**必须**落在 `INTEGER` 的有符号 64 位区间内,越界 ⇒ 解析失败。

**失败口径(内容级)**:解析失败**不是**诊断。`TO_INT` 返回一个 `ERR` 值,载荷是**字典** —— `kind` = `"ParseError"`、`input` = **原始**实参字符串(裁剪前的原串)、`reason` = 失败原因文本(措辞**不由**本规范冻结)。⇒ 程序**不**因此中止;调用方按语言核心册 §8.3 的 `IS_ERR` / `ERR_PAYLOAD` / `UNWRAP_OR` 分支处理该 `ERR`。空串、纯空白串、只有符号的串、含非数字字符的串 ⇒ 解析失败(同一形状的 `ERR` 值)。

**与全局内建 `INT` 的口径差异(故意不同)**:二者**不**是同一件事的两种写法。

| | `INT`(全局内建;语言核心册 §10.3.1) | `TO_INT`(本成员) |
|---|---|---|
| 空白 | **一律不裁剪** —— `INT(" 42 ")` 失败 | 裁剪首尾空白 |
| 进制 | 只接受十进制 —— `0x1F` / `1_000` / `1e3` 全部失败 | 另接受 `0x` / `0X` 十六进制文本 |
| 小数 | 字符串的小数形态**拒**(`INT("42.9")` 失败);截断只发生在实参本身是 `FLOAT` 时 | 小数截断 |
| 解析失败 | `ERR([kind: "ParseError", input, reason])` **值** | 同左 |
| 实参类型错 | `E0030`(诊断) | `E0030`(诊断) |

**分工理由**:`INT` 服务于**内部严格转换** —— 实参是程序自己产出的、形态已知的值,宽松接受只会把笔误变成静默的错误值;`TO_INT` 服务于**外部输入解析** —— 文本来自文件 / 命令行 / 网络,首尾空白与十六进制前缀是**常态**,把它们**拒**掉会把大量正常输入误判成错误。⇒ 调用方**必须**按输入来源选成员:形态已知的自有值用 `INT`,外来文本用 `TO_INT`。

⚠ 该差异已在**语言核心册 §10.3.1** 登记(「`INT` 是否与 `TO_INT` 统一」是**待裁决**的差异项)⇒ 本册只把 `TO_INT` 的宽松口径成文,**不**要求 `INT` 改变行为。

示例只覆盖参考实现已提供的成员;`TO_INT` 的读数见 §12.4。

## 13 `std.sanitize` —— 输出安全

**威胁模型**:本命名空间防的是「不可信数据在**输出点**被解释为代码或结构」。它**不**清洗输入(OWASP 现行口径:输入侧「清洗」不是 XSS / 注入的防治手段),**不**做语义校验(URL 是否可达、邮箱是否真实),**不**防逻辑漏洞。每个成员各自写明防什么、不防什么、被绕过时表现为什么。

**上下文分工口径(规范性,三者互不替代)**:不可信数据进入输出的安全手段**由输出上下文决定** ——

- **URL 上下文**(`href` / `src` 等属性的**值**):`URL_ENCODE`(RFC 3986,标准库·安全册 §11);
- **标记上下文**(HTML 文本节点与双引号属性值):`HTML_ESCAPE`(本章);
- **业务必须接受富 HTML** 时:`HTML_SANITIZE`(本章)—— 唯一能保留标记结构的手段。

选错上下文的转义(例如拿 URL 转义去填 HTML 文本)**不是**保守,是**错误**。

本章的语义参照 WHATWG HTML / WHATWG URL、CSSOM(W3C REC cssom-1)、CSS Syntax Module Level 3 与 OWASP 的输出转义 / XSS 防治指南;参考实现是 `Laffinty/wlwl`(基线提交 `99041ef`)。

| 签名 | 语义 | 失败 | 复杂度 | 层 |
|---|---|---|---|---|
| `HTML_ESCAPE(data) -> STRING` | 标记上下文转义(§13.1) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n) 最坏 | R2 |
| `HTML_UNESCAPE(data) -> STRING` | HTML 实体解码(**全表**,§13.1) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n) 最坏 | R2 |
| `HTML_SANITIZE(data, policy?) -> STRING` | 富 HTML 白名单净化(§13.2) | 实参类型错 → `E0030`(带名);元数错 → `E0022`;`policy` 形态错 → `E0030`(带名) | — | R2 |
| `HTML_SANITIZE_SCRIPT(value) -> STRING` | 把值加固成可安全内联的 `<script type="application/json">…</script>`(§13.4) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | — | R2 |
| `CSS_ESCAPE_IDENT(s) -> STRING` | 把字符串序列化成**合法 CSS 标识符**(类名 / `id` / 自定义属性名,§13.5) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n) 最坏 | R2 |
| `CSS_ESCAPE_STRING(s) -> STRING` | 把字符串序列化成 **CSS 字符串字面量**(两侧带 `"`,§13.5) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n) 最坏 | R2 |
| `HTML_SANITIZE_CSS(text) -> STRING` | 从**声明列表**里按白名单抽出安全声明(§13.5) | 实参类型错 → `E0030`(带名);元数错 → `E0022`;命中拒绝构造 → `ERR([kind: "SanitizeError"])` | O(n) 最坏 | R2 |
| `HTML_SANITIZE_URL(u) -> STRING` | 归一 + scheme 判定,返回可放进 `href` 的值(§13.5) | 实参类型错 → `E0030`(带名);元数错 → `E0022`;不接受 → `ERR([kind: "SanitizeError"])` | O(n) 最坏 | R2 |

**共享失败口径**:本章的失败分两类,**不得**混为一谈。

1. **原生诊断**(程序员错误):实参类型错 → `E0030`(带名);元数错 → `E0022`;`policy` 形态错 → `E0030`(带名)。诊断的触发与终止按语言核心册 §11 与 §11.4。
2. **内容级失败**(`ERR` 值):只有两个成员会产生 —— `HTML_SANITIZE_CSS` 命中拒绝构造时返回 `ERR([kind: "SanitizeError"])`,`HTML_SANITIZE_URL` 不接受该 URL 时返回 `ERR([kind: "SanitizeError"])`。`HTML_ESCAPE` / `HTML_UNESCAPE` / `HTML_SANITIZE` / `HTML_SANITIZE_SCRIPT` / `CSS_ESCAPE_IDENT` / `CSS_ESCAPE_STRING` **永不因内容失败**:解析与过滤**永不**因输入内容报错。

**复杂度口径**:本表 `n` 是输入的码点数(语言核心册 §18.1)。`HTML_SANITIZE` 与 `HTML_SANITIZE_SCRIPT` 的代价随输入与净化策略变化,规范**不**为其给出上界,故记 `—`;§13.2 另行规定的是**处理遍数**与**嵌套深度**的行为要求,不是本表的时间上界。

**值形状与边界**:

- `HTML_ESCAPE` 的转义集是闭合的五字符集:`&` `<` `>` `"` `'`。**非 ASCII 码点逐字节原样保留**,不做任何 Unicode 处理。
- `HTML_UNESCAPE` 的实体表是**全表**(§13.1):命名实体取 WHATWG 全量,含无分号变体;未知命名实体**原样保留**。
- `HTML_SANITIZE` 的输出是**净化后的标记串**,**不**保证与输入逐位相关(嵌套矫正的固有属性)。
- `HTML_SANITIZE_SCRIPT` 的输出是**整段 `<script>` 元素**,不是裸串。
- `CSS_ESCAPE_IDENT` 的输出是**合法 CSS 标识符**;`CSS_ESCAPE_STRING` 的输出是**带双引号的 CSS 字符串字面量**。
- `HTML_SANITIZE_CSS` 的输出是**CSS 源码片段**(声明列表),不是 CSS 数据值;没有任何声明存活时返回空串 `""`。
- `HTML_SANITIZE_URL` 的输出是**归一后的 URL 文本**(剥首尾空白与控制字符),可放进 `href`;**不**做大小写归一、**不**做百分号编码。

### 13.1 `HTML_ESCAPE` / `HTML_UNESCAPE` 的精确口径

**`HTML_ESCAPE`**:对 `&` `<` `>` `"` `'` 五个 ASCII 字符做实体转义,映射为 `&amp;` / `&lt;` / `&gt;` / `&quot;` / `&#39;`(`'` 用 `&#39;` 不用 `&apos;` —— 旧渲染器兼容口径);**非 ASCII 码点逐字节原样保留**,不做任何 Unicode 处理。适用于 HTML 文本节点与**双引号属性**值两种上下文(HTML5 同口径)。**属性值必须带引号**;未加引号的属性值不在本函数的契约内。

**`HTML_UNESCAPE`**:HTML 实体解码,**全表** ——

- **命名实体**:HTML5 全表(约 2 231 项,含无分号变体)。**实体表必须是全表**:实现**必须**正确解码 `&copy;` 一类实体,**不得**只认本库转义集而退化成半表行为。**未知命名实体原样保留**(HTML5 自身的容错行为,不是本库私货)。
- **数字引用**:`&#DDDD;` / `&#xHHHH;`,按 WHATWG 数字引用解析规则处理(码点越界 / 代理区映射为 U+FFFD 等);**溢出有检查,不得 panic**。

**roundtrip 定理**:`HTML_UNESCAPE(HTML_ESCAPE(s)) == s` 对一切 `s` 成立(本库转义集闭合)。本成员**就是**消费第三方 HTML 时的实体解码器 —— `HTML_SANITIZE` 的解析器复用同一张表。

### 13.2 `HTML_SANITIZE` 与净化策略

**形态(沿 ammonia / nh3 的现代口径)**:容错解析(WHATWG 精神,畸形输入按恢复规则处理,**不报错**)→ **白名单过滤** → 序列化。三段决定:

- 违规标签**删除**,不是转义;
- `script` / `style` 及其**内容**整体删除;
- 属性按逐标签白名单过滤;`href` / `src` 类 URL 属性过 **scheme 白名单**(大小写不敏感、控制字符剥离后再判,防 `jav&#x09;ascript:` 类绕过);
- 解析与过滤**永不因输入内容失败** —— 失败只有类型错 / 元数错 / `policy` 形态错三类原生诊断。

**策略(`policy`,可省)**:`DICT`,四键(全部可省;省略的键取**缺省策略**;出现的键**整体替换**缺省值,不是合并):

| 键 | 类型 | 缺省值 | 说明 |
|---|---|---|---|
| `"tags"` | ARRAY[STRING] | `a` `b` `blockquote` `br` `code` `em` `h1`–`h6` `hr` `i` `li` `ol` `p` `pre` `s` `strong` `u` `ul`(22 个,小写) | 允许保留的标签白名单;不在表内的标签**拆壳留内容**(unwrap),下列例外整棵删除 |
| `"attributes"` | DICT(键:标签名 → ARRAY[STRING];键 `"*"` 为全局属性) | `{"a": ["href", "title"]}`(`"*"` 缺省为空) | 逐标签属性白名单;不在表内的属性**删除** |
| `"url_schemes"` | `ARRAY[STRING]`(小写) | `["http", "https", "mailto"]` | URL 类属性(`href` / `src` / `action` / `formaction` / `poster` / `cite` / `background` / `data` / `srcset` / `longdesc` / `usemap` / `manifest` / `codebase` / `archive` / `dynsrc` / `lowsrc` / `icon` / `xlink:href`)的 scheme 白名单;**相对 URL 恒允许**;判定前先剥首尾空白与控制字符再取 `:` 前缀小写比较(实体已由解析解码) |
| `"strip_comments"` | BOOLEAN | TRUE | TRUE → 注释删除;FALSE → 保留,但注释内容中的 `--` 全部移除(防 `-->` 提前闭合) |

`policy` 形态不符(键值类型错、未知键、`tags` 元素非小写标识符等)→ `E0030` 带名。**未知键不得静默忽略** —— 策略里把键名拼错,静默忽略会把它变成「没配」。

**树构建与解析的子集(与浏览器解析器的差异,显式登记)**:

- 解析为**树**(非 token 流):维护开标签栈,实现白名单相关子集的 tree-construction 规则 —— `<p>` 在新块级标签开始时隐式闭合、`<li>` 闭合 `<li>`、`<dt>` / `<dd>` 闭合彼此、`<tr>` / `<td>` / `<th>` / `<thead>` / `<tbody>` / `<tfoot>` 互相按 HTML5 位次闭合;结束标签在栈内则弹到匹配处、不在栈内则忽略。
- **不实现**:foster parenting(表格外内容的搬移)、命名空间 / 外来内容(svg / math 整棵删除)、`<plaintext>` 后的全文文本化(按普通文本处理)、`</p>` 无对应开标签时的空元素生成(直接忽略)。**安全性由幂等性守护,不由「与浏览器相同」守护** —— 本成员的输出再次输入本成员**必须**逐字节不动。
- **raw-text 元素**(`script` / `style` / `textarea` / `title` / `xmp` / `noembed` / `noframes` / `iframe` 内文):内容不作为标记解析,整棵删除 —— 这些元素的删除集身份同时封掉了「raw-text 内容再解析」这一整类 mXSS 面。**整删集恰好就是这 8 个 raw-text 元素,不多不少**(整删集还含 `object` / `embed` / `noscript` / `template` / `svg` / `math` / `head` 等危险嵌入与外来内容)。**`<plaintext>` 不在整删集** —— 它不是 raw-text 元素,本成员不实现「其后全文文本化」,故按**普通非白名单元素**处理(拆壳留内容)。拆壳是就内容可恢复性而言更宽松,**不放宽内层任何判定**。
- **void 元素**(`br` / `hr` / `img` / `input` 等 14 个):无子节点,序列化为 `<name …>` 无结束标签。
- 未知 / 拆壳的标签,其**属性一并消失**(只有保留标签才谈属性白名单);同名属性重复时**首个生效**。
- 处理遍数:实现**必须**以一趟完成解析、一趟完成过滤、一趟完成序列化;深嵌套输入**不得**导致栈溢出。三条使该要求成立的实现细节:① **结束标签按标签名查「栈内最内层位置」**,判负是一次查表、**与栈深无关**,位置索引**必须**留**位置串**并随截断**自栈顶向下**清理;② **raw-text 的关闭扫描是原地滑窗**、**不**物化整个余文;③ **属性同名去重是哈希集合**,判负 / 判重都是 O(1)。

**安全不变量(规范性,打破即缺陷)**:**重解析幂等** —— `HTML_SANITIZE(HTML_SANITIZE(x, p), p) == HTML_SANITIZE(x, p)`(字节级)。依据:IEEE S&P 2024 与 Sonar mXSS 研究证明,解析模型与浏览器存在差分的净化器可被 mXSS 结构性绕过。**不承诺与浏览器解析逐位一致**:树构建实现的是 WHATWG 规则的**白名单子集**,差异显式登记。**往返不承诺**:输出不保证与输入逐位相关(嵌套矫正的固有属性)。

### 13.3 为什么没有 SQL 转义成员

**本命名空间不提供 SQL 注入用的字符串转义成员。** 实现**不得**新增 `SQL_ESCAPE` 一类成员。这不是遗漏,是裁决:

1. **OWASP 的定性是 last resort**:SQL 注入防治的位次是参数化查询(prepared statement)→ 存储过程 → 白名单校验 → **转义垫底** —— 转义易碎且方言分裂(MySQL 的反斜杠转义 vs 标准的双写引号、`NO_BACKSLASH_ESCAPES` 模式、LIKE 通配符另有一套),做错比不做更危险。
2. **wlwl 没有参数化收口**:`std.db` 不存在,调用方拿到的任何 `SQL_ESCAPE` 都只能手工拼串 —— 正是把 OWASP 排在最后的姿势当成第一防线。提供它等于**制造假安全感**。
3. **动态标识符(列名 / 表名)的正解是白名单映射**:把用户提供的名字映射到服务端固定值,而不是转义。这与 `HTML_SANITIZE` 的白名单哲学同源,同样不需要转义函数。
4. **复活条件**:`std.db`(或任何 SQL 互操作命名空间)落地时,防治手段以 prepared statement 形态提供;届时本条由该命名空间的规范接手。

### 13.4 `HTML_SANITIZE_SCRIPT`

本成员收**值**、产出**整段元素**:输出是 `<script type="application/json">` + 加固后的 JSON + `</script>`,不是裸串。

**加固动作**:对 `STRINGIFY(value)` 的输出,把 `<` `>` `&` U+2028 U+2029 五个字符逐个换成**大写十六进制**的 `\u003C` / `\u003E` / `\u0026` / `\u2028` / `\u2029`。**只转这五个** —— JSON 自身的 `\"` `\\` 与控制字符转义已由 `STRINGIFY` 负责。

**失败口径:全函数,且不因内容失败。** 加固把 `<` 全部消掉之后,输出里唯一的 `<` 是本成员自己写的开标签,任何输入都**无法**终止 script data 状态 ⇒ **没有任何值能让它出错**。

**本成员产出的 `application/json` 块必须由 `JSON.parse` 读取**;需要把数据**执行**而不是**读取**时,本成员**不**适用;跨域读取受同源策略约束,与本成员无关。

**明确不做**:`JS_ESCAPE_STRING` / `JS_ESCAPE_COMMENT`(通用字面量与注释转义)、JS 代码生成、把裸 JSON 交给 `eval` 的任何便利化。

**说明**:OWASP DOM XSS Prevention Cheat Sheet 明写 `JSON.stringify()`「**is not an output-encoding function**」,并逐字符点名内联场景还要额外挡住 `<`(及 `>` `&` U+2028 U+2029)—— 参考实现的 `STRINGIFY` 把这五个字符**全部原样输出**,缺口在标准库自己这边。OWASP 的**首选**也不是转义,而是「用 `Content-Type: application/json` 单独响应」或「走 `<script type="application/json">` 这个 inert 容器」;而通用 JS 字符串字面量转义剩下的用武之地(`onclick="f('…')"`)已被 `HTML_SANITIZE` 整条剥掉事件处理器属性覆盖掉。

**实现注(非规范)**:参考实现 `Laffinty/wlwl` 的 `STRINGIFY` 对 `<` `>` `&` U+2028 U+2029 五个字符原样输出,故本成员的加固是必需的,不是冗余。

### 13.5 CSS 上下文与 URL 上下文

**实现顺序按 OWASP 口径**:CSS 上下文指引的第一句是「**allowlist it**」,CSS-escape 是**补充** ⇒ `HTML_SANITIZE_CSS` 先于两个 `CSS_ESCAPE_*`。这与 §13.3 否掉 SQL 转义是同一条纪律:转义垫底、白名单当第一防线。

**`CSS_ESCAPE_IDENT` / `CSS_ESCAPE_STRING` 逐条照抄 CSSOM §"Common Serializing Idioms"**,不是自创规则。要点:

- 「转义一个字符」= `\` + 该字符;「按码点转义」= `\` + **最小位数小写十六进制** + **一个空格**。尾随空格是消歧符,漏了它 `\31 23` 会与 `\3123` 混。
- 标识符:`U+0000` → `U+FFFD`;`[U+0001-U+001F]` 与 `U+007F` 按码点转义;**首字符**数字按码点转义;**第二字符**数字且首字符是 `-` 按码点转义;单独的 `-` 转义为 `\-`;`>= U+0080` 与 `- _ 0-9 A-Z a-z` 原样;其余转义。
- 字符串:`"` + 内容 + `"`;`U+0000` → `U+FFFD`;控制字符按码点转义;`"` 与 `\` 转义;**其余原样**。**`'` 不转义** —— CSSOM 原文注明字符串**总是**用 `"` 序列化,单引号没有转义必要。
- **版本差异(契约冻结现行版)**:CSSOM 的这两条算法改过 —— 2013 WD 版对 `U+0000` 是**抛 `InvalidCharacterError`**,控制字符范围也更宽(`[U+007F-U+009F]`);**现行版**(W3C REC cssom-1)是 `U+0000` → **`U+FFFD`**、取 `[U+0001-U+001F]` + `U+007F`。本规范跟**现行版**。

**`HTML_SANITIZE_CSS` 的输出形态**:每条存活声明写成 `属性: 值`,**声明之间以 `;` 分隔**(尾随 `;` 保留)。**分隔符不可省** —— `color: red font-weight: bold` **不是**合法 CSS;属性名一律小写归一。**没有任何声明存活时返回空串 `""`**,不是一个孤零零的 `;`。

**`HTML_SANITIZE_CSS` 的两条分开失败口径**:

| 情形 | 结果 |
|---|---|
| 属性**不在白名单** | **静默丢弃**,产出里看不到它 —— 那是白名单**正常工作**的样子 |
| 命中**拒绝构造** | 整个输入判为攻击 ⇒ `ERR([kind: "SanitizeError"])` |

拒绝构造(文本级,**先于**解析扫描):`@import`、`expression(`、`javascript:`、`vbscript:`、`behavior:`、`-moz-binding`、**任意 `url(`**。

**任意 `url(` 一律拒**,不做「URL 看着安全就放行」—— 那需要解析 `url()` 的完整语法 + `data:` 的 MIME 白名单,是**另一个成员**的事。能取 `url()` 的属性(`background` / `cursor` / `content` / `filter` / `src` / `list-style-image` / `border-image`)**也一律不在白名单** —— 不靠单点防御。**解析范围只到声明级**(`prop: value` 对):**不做**选择器语义、**不做**值语法解析;但拒绝扫描是**文本级**的(先扫原文再解析),分号与冒号都**不在引号内、不在圆括号内**才算分隔符。

**拒绝扫描扫的是「原文 ∪ 按 CSS 转义解码后的原文」**。只扫原文是可绕过的:`e\78 pression(…)` 在字节层面根本不含 `expression(`,而浏览器**会**把它解码回去 ⇒ 扫描**必须**按 CSS Syntax Module Level 3 的 *Consume an escaped code point* 规则(该规范 4.3.7 节)解码后再比:反斜杠后**尽量多取十六进制、至多 6 位**,零 / 代理区 / 越界一律返 `U+FFFD`,遇到 EOF 同样 `U+FFFD`(解析错误),**非十六进制则该字符字面**;那个「顺带消费一个尾随空白」**只在十六进制分支**。解码结果**只喂扫描、不进输出**。**两份原文都要扫**:反斜杠在 token **之前**的写法(`\url(`)字面已含 token,只扫解码遍反而会漏。

**`HTML_SANITIZE_CSS` 的返回值是「CSS 源码片段」,不是 CSS 数据值**。声明值出函数前按 CSSOM §"Common Serializing Idioms" 的 *escape a character as code point*(`\` + 小写十六进制 + **一个空格**)逐字符加固,至少覆盖 `<` `>` `"` `'` `*` `;` `{` `}` `\` 与裸 CR / LF / FF。

**不能照抄 `HTML_SANITIZE_SCRIPT` 的 `\u003C`**:JS 字符串字面量的转义形状是 `\uXXXX`,CSS **没有这个形状** —— 照抄过去在 CSS 里只是标识符文本 `u003C`,`<` **原样留在输出里**,破壳照旧。两边形似而义不同,是本节最容易照错的一处。

**反斜杠必须与本文插入的转义一起加固**:CSS 里 `\` 后跟十六进制才是转义,调用方自带的 `\` 会与插入的 `\3c ` 连成别的序列,转义就不再是「值的逐字映射」。副作用是**有意的**:调用方自己写的嵌套 CSS 转义(中文字体名 `\5FAE\8BA4` 一族)被当数据处理,字体名退化为不匹配 → 回退默认字体。对**不可信数据**而言,嵌套转义语法正是拒绝扫描的绕过面,不能留给它。

**`HTML_SANITIZE_CSS` 在什么情况下不够用**(与 §13.4 同体例,成文):

1. **返回值必须原样内联**。它已经是可安全放进 `<style>` / `style="…"` 的源码片段;调用方若把它当字符串**数据**再拼进 CSS 上下文,会得到双份转义。
2. **不接受需要嵌套转义的字体名**。要安全地放进字体名,先过 `CSS_ESCAPE_STRING`。
3. 仍然**不做**:把返回值当 HTML 用(那是 `HTML_ESCAPE` 的活)、跨域读取(同源策略,与本成员无关)。

**本成员提供的保证值多少**:`expression()` 是 **IE5–IE9 的专有特性**,IE10 起被移除,其它引擎从未实现 ⇒ **现代浏览器不执行它**。因此本成员的真实防线是**两道**,而不是「堵住一个能打的洞」:① **白名单**(只有列出的属性与值能进);② **拒绝扫描**(把 `expression(` / `@import` / `javascript:` / `vbscript:` / `behavior:` / `-moz-binding` / 任意 `url(` 挡在外面)。其中 `@import` 与 `url(` **即便被绕过也无出口** —— 能取 `url()` 的属性(`background` / `background-image` / `cursor` / `content` / `filter` / `src` / `list-style-image` / `border-image`)**一律不在白名单**。本成员**不是**「浏览器沙箱」—— 它是**上下文转义 + 白名单**的组合,不是同源策略或 Trusted Types 的替代品。

**`HTML_SANITIZE_URL` 与 `HTML_SANITIZE` 的 URL 属性判定是同一份逻辑**,默认 scheme 列表同为 `http` / `https` / `mailto`。两者的结论**必须**一致;**不得**各写一份 —— 否则会出现「净化器放行、独立成员拒绝」的分裂,而分裂意味着其中一处是错的。

**说明**:那条「一致」契约只断言一致、不断言哪个结论 —— 两处**同时**错也照样绿。它守的是「别分裂」,不是「别都错」。

**相对 URL 的判定是位置性的**:剥首尾控制字符与空白后,**第一个** `/` `?` `#` **之前**出现的那个 `:` 才是 scheme 的结尾;落在它们**之后**的 `:` 是路径段 / 查询 / 片段内部的分隔符 ⇒ 该值是**相对 URL**,**恒允许**,不进 scheme 白名单比对。依据 WHATWG URL 的 4.2 节 *scheme start state* ≡ RFC 3986 的 3.3 / 3.4 / 3.5 节。**豁免必须排在「scheme 形态合法性」判定之前** —— 顺序反了会把 `/wiki/special` 当成非法 scheme 而拒掉。

**不做大小写归一、不做百分号编码**:路径大小写敏感,小写化会**改错资源**;百分号编码是 URL 上下文自己的事(标准库·安全册 §11 的 `URL_ENCODE`)。本成员只做**安全判定需要**的那一步归一(剥首尾控制字符与空白)。

**实现注(非规范)**:拒绝时的 `ERR` 载荷是 `["kind": "SanitizeError"]`;参考实现另附被拒的 `scheme` 字段,实现**可以**附带同类诊断字段。

### 13.6 示例

```wlwl
IMPORT("wlwl:std.sanitize", ["HTML_ESCAPE", "HTML_UNESCAPE", "HTML_SANITIZE", "HTML_SANITIZE_SCRIPT", "CSS_ESCAPE_IDENT", "CSS_ESCAPE_STRING", "HTML_SANITIZE_CSS", "HTML_SANITIZE_URL"]);
PRINT(HTML_ESCAPE("<a href=\"x\">&</a>"));  // &lt;a href=&quot;x&quot;&gt;&amp;&lt;/a&gt;
PRINT(HTML_UNESCAPE("&lt;b&gt;"));           // <b>
PRINT(HTML_UNESCAPE("&copy;"));             // ©
PRINT(HTML_SANITIZE("<p onclick=\"x\">hi</p><script>bad</script>"));  // <p>hi</p>
PRINT(HTML_SANITIZE_SCRIPT(["a": "<b>"]));  // <script type="application/json">{"a":"\u003Cb\u003E"}</script>
PRINT(CSS_ESCAPE_IDENT("a b"));             // a\ b
PRINT(CSS_ESCAPE_STRING("a\"b"));           // "a\"b"
PRINT(HTML_SANITIZE_CSS("color: red; font-weight: bold"));  // color: red; font-weight: bold;
PRINT(HTML_SANITIZE_URL("https://example.com/a"));  // https://example.com/a
```

### 13.7 设计依据(非规范)

本节是**非规范**的追溯材料,不构成一致性要求。

本命名空间随 v0.11.3 M1 / M3 / M7 落地;转义 / 解码 / 净化全员 R2 —— 它们都要处理**文档级输入**,而解释器侧字符串与数组构建是超线性的(与 `RANGE` 沉回 R2 同一根因)。上游 `Laffinty/wlwl` 的 `ADR-0030` D2 记了 `JS_ESCAPE_*` 的否决与 `HTML_SANITIZE_SCRIPT` 的换题;`ADR-0030` D3 记了 Trusted Types 范式的否证(复活条件:wlwl 出现**宿主形态**)。

**为什么收整个元素而不是裸串**:若只暴露一个「转义裸串」的成员,调用方可能忘记调、可能只转一半、可能转完又拼回去 —— 那它提供的安全感和裸拼字符串没有区别。收**值**、由成员自己 `STRINGIFY` + 加固 + 包壳,「忘记加固」这个失败模式就**不存在**,而不是靠文档提醒。这与 `HTML_SANITIZE` 收整段标记、`HTML_SANITIZE_URL` 收整个 URL 是同一个族。

**为什么 §13.5 扫描两遍原文**:反斜杠在 token **之前**的写法字面已含 token,只扫解码遍会漏;只扫原文则会被 CSS 转义绕过。两遍并取是唯一同时堵住两个入口的读法。

上游偏差台账中与本章相关的条目:`D13-009`(policy 合法键的报错形状)、`D13-022`(`HTML_SANITIZE_CSS` 返回值形状)、`D13-023`(相对 URL 判定)、`D13-058` / `D13-059` / `D13-062`(三条处理遍数要求的实现细节)、`D13-070`(拒绝扫描的解码遍)。

## 16 `std.regex` —— 线性时间正则

**立身之本是「执行时间对输入线性」。** 实现走 Thompson 构造 + Pike VM,**没有回溯**。§16.3 的「必须拒绝」那一组不是功能取舍,是这条承诺的**前提**:一旦允许回溯引用或 lookahead,指数爆炸就成了可能,那这个成员等于没做。

本章的语义参照 RE2 的语法文档(`doc/syntax.txt`)、Go `regexp/syntax` 的实现口径,以及 Perl / Python / JavaScript 的正则行为;参考实现是 `Laffinty/wlwl`(基线提交 `99041ef`)。

### 16.1 成员

| 签名 | 语义 | 失败 | 复杂度 | 层 |
|---|---|---|---|---|
| `RE(pattern) -> DICT` | 编译成**模式对象** `[pattern, groups]` | 模式语法错 → `E0030`(带**列号**);实参类型错 → `E0030`(带名);元数错 → `E0022` | O(p) | R2 |
| `RE_TEST(re, s) -> BOOLEAN` | **整串**是否匹配(两端锚定,且**忽略** `(?m)` —— 整串的语义是「整个输入被消费完」) | 实参类型错 → `E0030`(带名);元数错 → `E0022`;**永不因内容失败** | O(n·p) 最坏 | R2 |
| `RE_SEARCH(re, s) -> DICT 或 NULL` | 第一个匹配:`[matched, start, end, groups]`;`start` / `end` 是**码点**下标(与 `CHAR_AT` / `INDEX_OF` 同一坐标系),**不是**字节偏移 | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n·p) 最坏 | R2 |
| `RE_FIND_ALL(re, s) -> ARRAY of DICT` | 全部**非重叠**匹配,逐项形状同 `RE_SEARCH` | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n·p) 最坏 | R2 |
| `RE_REPLACE(re, s, repl) -> STRING` | 替换全部非重叠匹配;`repl` 里 `$0` 是整体、`$1`… 是数字捕获组 | 实参类型错 → `E0030`(带名);元数错 → `E0022`;`${…}` 命名组 → `E0030` | O(n·(p+m)) 最坏 | R2 |
| `RE_SPLIT(re, s) -> ARRAY of STRING` | 按匹配切分(匹配本身不保留);**空匹配不做切分点** | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(n·p) 最坏 | R2 |
| `RE_GROUP_COUNT(re) -> INTEGER` | 捕获组个数(不含整体) | 实参类型错 → `E0030`(带名);元数错 → `E0022` | O(p) | R2 |

**复杂度口径**:本表 `n` 是主串的码点数、`m` 是替换串的码点数、`p` 是编译后指令数(语言核心册 §18.1 的 `n` / `m` 记法在此扩展)。匹配成员的上界写作 O(n·p):**模式固定时即对输入线性**,这正是本章的立身之本;模式规模随调用方变化时,乘积项 `p` **不**可省。

**共享失败口径**:**不匹配不是错误。** `RE_*` 返回成功值或 `NULL`;唯一的原生诊断是元数错 / 类型错 / 编译错。正则不匹配是**正常的业务分支**,做成 `ERR` 会逼调用方到处 `ERR_PAYLOAD`。

`RE` 之外的成员,第一个实参**必须**是 `RE` 返回的模式对象;裸模式串或其它形态产生 `E0030`。模式语法错在**编译期**以 `E0030` 中止(带**列号**)。

**值形状与边界**:

- `RE` 的返回值是 `DICT`,含 `pattern`(模式源串)与 `groups`(组数,整数)两键。`RE_GROUP_COUNT` 取的正是其中的组数,调用方**不**必为拿组数再编一遍。
- `RE_SEARCH` / `RE_FIND_ALL` 的每项形状是 `DICT`,含 `matched`(匹配文本)、`start` / `end`(**码点**下标)与 `groups`(捕获组数组,第 0 项是整体匹配)。
- 不匹配时:`RE_TEST` 返回 `FALSE`,`RE_SEARCH` 返回 `NULL`,`RE_FIND_ALL` 返回空数组,`RE_REPLACE` 返回原串,`RE_SPLIT` 返回单元素数组。
- `RE_SPLIT` 的匹配本身**不**保留;**空匹配不做切分点**。

### 16.2 语义:左最早,不是左最长

多个分支都可能匹配时,wlwl 取**左最早(leftmost-first)** —— 也就是「一个回溯引擎最先找到的那个」,**与 Perl / Python / JS / Java / Rust `regex` 一致**。

**这里刻意不跟 RE2 的默认。** RE2 的默认也是 leftmost-first,而**左最长(leftmost-longest)是它的 POSIX 模式**;选它会让 wlwl 成为唯一异类,而正则跨语言移植是日常操作。另一条理由:Go 的文档承认 POSIX 的子选择规则「计算上不可承受甚至没有良定义」,它自己的 `CompilePOSIX` 也没完全遵守。

**说明**:**线性时间来自 NFA 模拟,与选哪条语义无关** —— 没有性能理由偏向任何一方。

### 16.3 **必须**拒绝的构造(与线性时间互斥)

`(?=…)` / `(?!…)`(lookahead)、`(?<=…)` / `(?<!…)`(lookbehind)、`\1` / `(?P=…)`(**回溯引用**)、`(?<name>…)`(命名组)、`\p{…}`(Unicode 类别)、反向正则、零宽断言 —— **一律在编译期 `E0030`**,**不得**静默放行。**它们不是「以后再加」**:允许其中任何一条,线性承诺当场破。

**零宽断言含转义形式 `\b` `\B` `\A` `\z` `\Z`**。这五个在 Perl / Python / PCRE / RE2 里都是**正宗的零宽锚点**,从那些生态过来的人几乎必然会写到 ⇒ 实现**必须**给出指名报错的 `E0030`,**不得**静默当字面量。**字符类内同样拒**(`[\b]`):类外与类内是同一个缺口的两个入口,只堵一个会留下另一半。口径与 Go `regexp/syntax` 一致(它在类内也报 `invalid escape sequence`)。

**说明**:零宽断言在 Thompson NFA 上要**分支**而不是消费字符 —— 那会让一次抵达同时对应「锚点前」与「锚点后」两条路径,§16.2 的 leftmost-first 裁决键随之不再是良定义的。反向引用的实测后果:`(a*)*b` 在 10 000 个 `a` 上,回溯引擎跑不完,而本成员**立刻返回「不匹配」**。

### 16.4 四条容易踩的细节

1. **`.` 默认不含换行**,`(?s)` 让它匹配一切(依据 RE2 `re2.h` 的 `dot_nl (false)`)。
2. **`^` / `$` 默认锚整个输入**,`(?m)` 切到行锚点。**刻意不抄 RE2 的 `m` 命名** —— RE2 的 `(?m)` 语义与 Perl **相反**(它的 `one_line` 才是「只在文本首尾」),而从 Perl / JS / Python 过来的人对 `m` 的直觉是「多行 = 行锚点」。跟直觉走。**`$` 是 `\z` 语义、不是 `\Z`**:RE2 `doc/syntax.txt` 原文 "text end (**like `\z` not `\Z`**)" ⇒ **不匹配结尾换行之前**。这与 RE2 / Go **一致**;与 **Perl / Python** 的 `$` 不同 —— 后者在结尾换行**前**也成立,而 RE2 把那个形态叫 `\Z` 并标注 **NOT SUPPORTED**。⇒ 从 Perl / Python 过来的人若要「换行前也成立」,**本成员给不了**,且**不会假装给**。
3. **`\w` `\d` `\s` 与 `(?i)` 都是 ASCII-only**。Unicode 大小写折叠走 `std.text`(§12)—— 两套口径混在一起会让「为什么 `\w` 不匹配 `é`」变成一件说不清的事。
4. **`(?i)` / `(?s)` / `(?m)` 的作用域比 RE2 / Go 窄**。本成员是「到**本分支**结束」;RE2 `doc/syntax.txt` 原文 `(?flags)` = "set flags **within current group**" ⇒ RE2 / Go 是「到**所在 group 的右括号**」;Go `regexp/syntax` 的 `parse.go` 同证(标志在闭合括号处才恢复,`|` **不恢复**)。⇒ **`(a(?i)b|c)` 上两者结果不同**:RE2 让 `c` 也忽略大小写,本成员不。**改成 RE2 口径要在整个 group 层共享标志而非每分支拷贝,属结构变更,本版不修**。

### 16.5 已知限制

- **`TRY_RE` 本册不做**:模式来自用户输入时**无法**「试编译不中止」。理由是不对称 —— 加成员是**附加式**(日后加不破坏任何东西),而**改失败形态是破坏式**,所以先把破坏的那条定死。
- **无命名组**(见 §16.3);`RE_REPLACE` 见到 `${…}` 报 `E0030` 而不是原样输出。
- **量词计数上限 1000、编译后指令数上限 64 K**:超出的模式报 `E0030`。这防的是「模式把**编译期**打爆」,与**输入长度**无关 —— 线性承诺说的是输入。
- **括号嵌套深度上限 256**:超出的模式报 `E0030`「pattern nests too deeply」。**这道闸不能省,也不能等编译期闸兜底**:2 万层 `((((…))))` 只产出 2 万条指令,「指令数上限」过得去,但解析递归、编译递归与 `AST` 析构递归**全部爆栈**;而栈溢出是 `abort` 不是 unwind,`catch_unwind` 接不住 —— 纯输入会带走整个解释器进程,而不是本节承诺的「编译期 `E0030` 优雅中止」。取 256 是**量出来的**:Go `regexp/syntax` 的 `maxNestDepth` 是 1000,但每层嵌套要占四个栈帧,而调用方线程栈不保证有 8 MiB。**这条是可证的边界**,改闸时**必须**同步改契约测试的 `deep_nesting_is_rejected_not_crashed`,它钉住闸的两侧。
- **码点坐标系**:一切位置与长度都是码点,不是字节。
- **内存形状**:本册承诺的是「执行时间对输入线性」,不是「内存对输入 O(1)」。`RE_FIND_ALL` / `RE_REPLACE` / `RE_SPLIT` 三条路径会为候选表分配**每输入起点 4 字节**的稠密索引 ⇒ 该路径的辅助内存是 **O(输入长度)**。这**不改变渐近阶**(输入本身就要 O(n) 的字符数组),它只改变常数;而候选集合本身是 O(不同起点数) ⇒ 把稠密索引换成哈希表**不改变渐近阶、且丢掉 O(1) 查表**,净收益为负 ⇒ 本册**不规定**更小的内存上限,也不承诺「`find_all` 是 O(1) 内存」。`RE_TEST` / `RE_SEARCH` 两条路径**不分配**该表。内存占用整体**不**承诺(语言核心册 §18.5)。
- **`RE_REPLACE` 对「越界组号」静默展开成空串**:`$5` 在模式只有 1 个组时**不报任何错**,直接展开成空串。依据:「组存在但没参与这次匹配」与「组号越界」**不可区分** —— 两者都是空串,后者是 Python / Go 的既定行为。对照:`${name}` 见到就 `E0030`;`$999…9`(超出 `usize`)解析失败也 `E0030`。**Python 在这里报 `invalid group reference`、Go 原样输出 `$5`** —— 三家三种行为,本成员跟的是「空串」那一档。改成报错属**可观察行为变更**,须单独立项,本版**不修**。

**实现注(非规范)**:参考实现对 `RE_*` 的每次调用都重新编译模式(不信任调用方传回的 `DICT`),因此 `RE_GROUP_COUNT` 当前是 O(p);模式对象已携带组数,实现**可以**缓存编译结果并以 O(1) 回答。

### 16.6 示例

```wlwl
IMPORT("wlwl:std.regex", ["RE", "RE_TEST", "RE_SEARCH", "RE_FIND_ALL", "RE_REPLACE", "RE_SPLIT", "RE_GROUP_COUNT"]);
PRINT(RE_TEST(RE("a+"), "aaa"));              // TRUE
PRINT(RE_SEARCH(RE("(a)(b)"), "ab"));         // [matched: ab, start: 0, end: 2, groups: [ab, a, b]]
PRINT(RE_FIND_ALL(RE("a"), "banana"));        // [[matched: a, start: 1, end: 2, groups: [a]], [matched: a, start: 3, end: 4, groups: [a]], [matched: a, start: 5, end: 6, groups: [a]]]
PRINT(RE_REPLACE(RE("(a)(b)"), "ab", "$2$1")); // ba
PRINT(RE_SPLIT(RE(","), "a,b,c"));            // [a, b, c]
PRINT(RE_GROUP_COUNT(RE("(a)(b)")));          // 2
PRINT(RE_TEST(RE("z"), "abc"));               // FALSE
PRINT(RE_SEARCH(RE("z"), "abc"));             // NULL
```
