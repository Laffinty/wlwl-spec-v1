## 0 导言与总则

### 0.1 本册的构成

本册定义 WLWL 标准库的**编码与哈希**部分:`std.encode`(§11,编码与哈希)。每章对应一个命名空间,每章含成员表(签名 / 语义 / 失败 / 复杂度 / 层)、共享失败口径、值形状与边界、示例与该章特有条款;附录 A 是**规范性**的成员注册镜像,由[标准库·注册镜像册](wlwl-v1.0-stdlib-registry.md)承载。

**成员数以附录 A 镜像为准**:本册各章的成员表与附录 A **逐项对拍**,两者**必须**集合相等。

全局内建(`PRINT` / `LEN` / `FORMAT` 等)**不在**本册重复定义,见语言核心册 §10.2–§10.5、§10.7、§10.9、§10.12 与其附录 G。

### 0.2 读者

本册面向三类读者:使用标准库的 WLWL 程序员、标准库实现者,以及需要判断某个成员行为是否合规的工具作者。

### 0.3 规范性用语

本册中的关键词 **必须**(MUST)、**不得**(MUST NOT)、**应当**(SHOULD)、**可以**(MAY)按以下含义使用:

- **必须 / 不得**:实现的硬性约束。违反时实现必须产生一个诊断(语言核心册 §11)并按 §11.4 终止或报告。
- **应当**:强烈推荐的行为;实现可以偏离,但偏离必须在本册或实现文档中说明。
- **可以**:真正的实现自由度。

标注为**非规范**(non-normative)的段落、注释与附录不构成一致性要求。

### 0.4 一致性

一个 WLWL 程序是符合本规范的,当且仅当它只使用本册定义的成员面,并按各章的语义与失败口径使用它们。一个实现是一致的,当且仅当它提供本册各章列出的全部成员,对每个成员给出规定的签名、语义、失败行为与边界,且不依赖任何标注为未定义、保留或实现定义的行为。

### 0.5 记法

成员表统一为**五**列:

| 列 | 含义 |
|---|---|
| 签名 | 成员名与形参;`?` 表示可选形参;`...` 表示变参 |
| 语义 | 正常路径的可观察行为 |
| 失败 | 失败时的可观察行为;`—` 表示**不因输入内容失败**。实参层诊断(元数错 `E0022`、类型错 `E0030`)适用于**全部**成员,由语言核心册 §8 与 §11.2 统一规定;各章**可以**重复列出以便查阅 |
| 复杂度 | 时间代价上界,记法见语言核心册 §18;`—` 表示规范不约束 |
| 层 | 实现分层(§0.7);R0 内建层 / R1 语言层 / R2 原生层 |

正文中的 `code` 样式表示词法记号、字面代码或诊断码。示例代码以 `//` 注释标出其求值结果。值形状用 `json` 标记的代码块给出。

**标点约定**:逗号 `,`、冒号 `:`、分号 `;`、圆括号 `()`、方括号 `[]` 一律用**半角**;句号 `。`、顿号 `、`、引号 `「」`、破折号 `——` 用**全角**。

**围栏约定**:文法块用**无标记**围栏;示例代码块用 **`wlwl`** 标记的围栏,且**必须**能在参考实现上运行且退出码为 0。

**失败示例的记法**:预期产生诊断的片段**不**写成 `wlwl` 围栏 —— 它们以非零退出码终止,不是可运行示例。本册用表格列出失败形态与预期诊断码。

**引用**:同册内写 `(§5.2)`;跨册写册名加节号,例:"语言核心册 §8.2"、"并发册 §17.3"、"一致性册 §3"。

**规范性标注**:本册**全部**为**规范性**;各章的「设计依据」小节是**非规范性**的追溯材料,不构成要求。

### 0.6 调用面

标准库的调用面只有两种形式,与实现层无关:

- **全局内建**(R0 内建层):无须导入;契约见语言核心册 §10.2–§10.5、§10.7、§10.9、§10.12 与其附录 G。本册不重复、不镜像全局内建。
- **命名空间成员**:`IMPORT("wlwl:std.X", [names])` 导入后调用;成员契约见本册各章。官方包 `ai` / `agent` 的导入路径分别是 `ai:ask` 与 `agent:task`。

**本语言没有「命名空间限定调用」表达式**:文法里没有 `ns.MEMBER(...)` 这种形式,冒号只出现在 `IMPORT` 的路径字符串与改名处。成员只能经 `IMPORT` 取裸名;需要避开与类型名同名时,在 `IMPORT` 时改名。

### 0.7 实现分层

| 层 | 实现语言 | 内容 |
|---|---|---|
| R0 内建层 | 纯 Rust(编译器/运行时内部) | 语言自身无法表达或与编译器强耦合的原语;即语言核心册附录 G 全部条目 |
| R1 语言层 | 纯 wlwl(`.wll` 源码,`include_str!` 嵌入二进制) | 不触系统调用且非性能敏感的库;**非敏感库的默认归宿** |
| R2 原生层 | 纯 Rust(`wlwl-std`) | 触系统调用、性能敏感、或需复用成熟 Rust crate 的库 |

**归属判定**(机械执行):

1. 触系统调用 / OS 资源 / 进程·网络·时间·随机 → R2;
2. 语言核心语义 → R0;
3. 其余 → R1;仅当基准数据证明热点且解释器短期无优化空间时下沉 R2;
4. R2 成员**必须**有不依赖实现细节的语义描述,保证可被 R1 等价替换。

**层间规则**:R1 **可以**调用 R0 与 R2;R2 **不得**调用 R1(确需时走白名单并登记偏差)。混合模块以门面(R1 侧)为对外契约层。层归属变更(下沉/上浮)**不算**破坏性变更,但**必须**附基准数据并登记。

**R0 / R1 / R2 是实现分层,不是规范层级。** 成员的规范强度与它落在哪一层**无关** —— 一个 R1 成员与一个 R2 成员承担同样的规范性义务(总纲 §0.6 规则 1)。

### 0.8 与语言规范的依赖与差异登记

本册以语言核心册 的值域、错误模型、模块机制、诊断码表、并发语义、复杂度保证与内存模型为前提,不重复定义。两册冲突时**以语言核心册为准**。

本册**唯一**的跨册差异登记是:`ERR` 的产生与消费规则。语言核心册 §8.6 规定"未消费的 `ERR` **不得**被丢弃",本册各章的「失败」列**只**描述成员自身在失败时**返回什么**,**不**复述 §8.6 —— `ERR` 值的丢弃与报告一律由 §8.6 承担。

## 11 `std.encode` —— 编码与哈希

base64(RFC 4648 §4)、hex、percent-encoding(RFC 3986 §2),以及单向摘要、口令派生、随机源与常数时间比较。

编码类成员都作用在**字节**上,而本语言的 `STRING` 是 UTF-8:编码成员**必须**取实参的 UTF-8 字节,解码成员**必须**在结果为合法 UTF-8 时才交出 `STRING`。摘要类成员同口径取 UTF-8 字节。

本节 `n` 取被操作文本的 **UTF-8 字节数**;`TIMING_SAFE_EQ` 取两段实参字节长度的较大者,`RANDOM_BYTES` / `RANDOM_HEX` 取请求的字节数。语言核心册 §18.1 对字符串默认取码点数 —— UTF-8 每码点占 1 到 4 字节,两者相差一个常数因子,故上界一致。

### 11.1 失败口径

本章的失败分三类,处置路径互不相同:

| 类别 | 触发 | 形态 |
|---|---|---|
| 程序员错误 | 元数不符、实参类型不符、KDF 参数越界、`algo` 取值未知、`salt` 不是偶长十六进制文本、`RANDOM_BYTES` / `RANDOM_HEX` 的 `n` 为负 | 原生诊断 `E0022` / `E0030` |
| 数据违例 | 解码输入畸形,或解出的字节不是合法 UTF-8 | `ERR` 值,载荷 `kind` = `"DecodeError"` |
| 环境失败 | 操作系统熵源读失败 | 原生诊断 `E0060` |

**解码失败是域违例**,返回 `ERR` **值**而不是诊断。它**不**叫 `DomainError` —— 把「`SQRT(-1)`」和「base64 串少了一个字符」归成同一个 `kind`,会让调用方没法区分。

**编码永不失败**:三个 `*_ENCODE` 成员的「失败」列是 `—`。

解码失败的 `ERR` 载荷**必须**是字典,含 `kind` / `op` / `reason` 三个键:

```json
{
  "kind": "DecodeError",
  "op": "BASE64_DECODE",
  "reason": "illegal base64 character '!'"
}
```

`op` **必须**取触发失败的成员名。`reason` 是人类可读的说明文本,其**具体措辞不构成规范**;`kind` 与 `op` 的取值**必须**如上。

**失败示例的记法**:预期产生诊断的片段**不**写成 `wlwl` 围栏 —— 它们以非零退出码终止,不是可运行示例。本章用表格列出失败形态与预期诊断码。

| 失败形态 | 预期诊断 |
|---|---|
| 元数不符(如 `SHA256()` 少一个实参、`TIMING_SAFE_EQ("a")` 少一个实参) | `E0022` |
| 实参类型不符(如 `SHA256(1)`) | `E0030` |
| `PBKDF2_ITER` 的 `iter` ∉ [600 000, 10 000 000] | `E0030` |
| `PBKDF2_ITER` 的 `len` ∉ [1, 1024] | `E0030` |
| `PBKDF2_ITER` 的 `algo` 不是 `"sha256"` | `E0030` |
| `PBKDF2_ITER` / `ARGON2ID` 的 `salt` 不是偶长十六进制文本 | `E0030` |
| `ARGON2ID` 的 `t_cost` ∉ [2, 32] | `E0030` |
| `ARGON2ID` 的 `m_cost` ∉ [19 456, 1 048 576] KiB | `E0030` |
| `ARGON2ID` 的 `p_cost` ∉ [1, 16] | `E0030` |
| `ARGON2ID` 的 `len` ∉ [4, 1024] | `E0030` |
| `ARGON2ID` 的 `salt` 解码后不足 8 字节 | `E0030` |
| `RANDOM_BYTES` / `RANDOM_HEX` 的 `n` 为负 | `E0030` |
| 操作系统熵源读失败 | `E0060` |

解码成员的失败形态全部返回 `ERR` 值,**不**产生诊断:

| 失败形态 | 所属成员 |
|---|---|
| 出现非法字符 | `BASE64_DECODE` / `HEX_DECODE` / `URL_DECODE` |
| 补位之后仍有数据 | `BASE64_DECODE` |
| 补位数大于 2 | `BASE64_DECODE` |
| 补位后总字符数不是 4 的倍数 | `BASE64_DECODE` |
| 未补位时长度 ≡ 1 (mod 4) | `BASE64_DECODE` |
| 末组残留非零位 | `BASE64_DECODE` |
| 十六进制长度为奇数 | `HEX_DECODE` |
| 百分号转义被截断 | `URL_DECODE` |
| 百分号转义含非十六进制字符 | `URL_DECODE` |
| 解出的字节不是合法 UTF-8 | 三个解码成员 |

### 11.2 成员表

| 签名 | 语义 | 失败 | 复杂度 | 层 |
|---|---|---|---|---|
| `BASE64_ENCODE(s, url_safe?) -> STRING` | RFC 4648 标准字母表 + `=` 补齐;`url_safe=TRUE` 换用 URL 字母表(`+/` → `-_`),缺省为 `FALSE` | — | `O(n)` | R2 |
| `BASE64_DECODE(s) -> STRING` | 忽略 `CR` / `LF`(base64 常被折行嵌入);**两张字母表都收**(见 §11.3 第 1 条);**补位可省略**(RFC 4648 §3.2),但**一旦出现 `=`,总字符数必须是 4 的倍数** | 失败 → `ERR([kind: "DecodeError", op, reason])` | `O(n)` | R2 |
| `HEX_ENCODE(s) -> STRING` | 小写、无分隔符 | — | `O(n)` | R2 |
| `HEX_DECODE(s) -> STRING` | 大小写都收;不忽略任何字符 | 失败 → `ERR([kind: "DecodeError", op, reason])` | `O(n)` | R2 |
| `URL_ENCODE(s) -> STRING` | percent-encoding;`unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"`,其余 `%XX`(大写十六进制) | — | `O(n)` | R2 |
| `URL_DECODE(s) -> STRING` | 解 `%XX`;**`+` 不折成空格**(见 §11.3 第 2 条) | 失败 → `ERR([kind: "DecodeError", op, reason])` | `O(n)` | R2 |
| `SHA256(data) -> STRING` | SHA-256(FIPS 180-4);输入按 UTF-8 字节,输出**小写十六进制**(64 字符) | 元数错 `E0022`;类型错 `E0030` | `O(n)` | R2 |
| `HMAC_SHA256(key, data) -> STRING` | HMAC-SHA256(RFC 2104);`key` / `data` 均按 UTF-8 字节;密钥超过块长(64 字节)先哈希再补零 | 元数错 `E0022`;类型错 `E0030` | `O(n)` | R2 |
| `PBKDF2_ITER(password, salt, iter, len, algo) -> STRING` | PBKDF2-HMAC-SHA256(RFC 8018 §5.2);`salt` 是**十六进制文本**;输出**小写十六进制**。`algo` 当前**只接受 `"sha256"`** —— 签名保留该形参是留位,SHA-512 不提供(见 §11.5) | 参数越界、`algo` 取值未知、`salt` 非偶长 hex、类型错 → `E0030`;元数错 `E0022` | `O(n)`(哈希部分) | R2 |
| `ARGON2ID(password, salt, t_cost, m_cost, p_cost, len) -> STRING` | Argon2id(RFC 9106,v = 19);`m_cost` 单位 KiB;`salt` 是**十六进制文本**;输出**小写十六进制**。**参数全部显式,无默认值** | 参数越界、`salt` 非偶长 hex 或解码后不足 8 字节、类型错 → `E0030`;元数错 `E0022` | `O(n)`(哈希部分) | R2 |
| `RANDOM_BYTES(n) -> ARRAY[INTEGER]` | **操作系统熵源(CSPRNG)**;返回 `n` 个 `INTEGER`(0–255)的**数组**,不是 `STRING` | `n` 为负 → `E0030`;熵源读失败 → `E0060`;元数错 `E0022`;类型错 `E0030` | `O(n)` | R2 |
| `RANDOM_HEX(n) -> STRING` | `RANDOM_BYTES` 的十六进制文本形态,`2n` 个**小写**字符。**本语言里生成 KDF 盐的正确方式** | `n` 为负 → `E0030`;熵源读失败 → `E0060`;元数错 `E0022`;类型错 `E0030` | `O(n)` | R2 |
| `TIMING_SAFE_EQ(a, b) -> BOOLEAN` | **常数时间**比较两段 `STRING`(按 UTF-8 字节);**永不失败** —— 长度不等是 `FALSE` 而非错误 | 元数错 `E0022`;类型错 `E0030`。**无其它失败** | `O(n)` | R2 |

**两个 KDF 的总代价由迭代参数决定,不由输入大小决定。** 成员表里那两个 `O(n)` 只计哈希部分(对输入字节数线性);`PBKDF2_ITER` 的实际代价由 `iter` 决定,`ARGON2ID` 的实际代价由 `t_cost` / `m_cost` / `p_cost` 决定。两者**不得**被读成「口令越长越慢」。

#### 11.2.1 值形状与边界

**`RANDOM_BYTES` 返回整数数组,不是 `STRING`** —— 这是本语言唯一能无损承载任意字节串的形态。名字说的是「字节」,而 wlwl 没有字节类型;硬塞进 `STRING` 只能把非法 UTF-8 有损替换成 `U+FFFD`,而本册**不**提供有损替换(§11.3 第 3 条)。**要文本就用 `RANDOM_HEX`。**

**`RANDOM_BYTES` / `RANDOM_HEX` 刻意不设长度上界。** 两个 KDF 设上界是因为「一个参数能打满机器」是**安全**问题;随机缓冲区调大只是多花时间与内存,而一个 wlwl 程序本来就能建更大的数组。`n = 0` **合法**,返回空数组 / 空串。

**熵源读失败是 `E0060`(IO error)而不是 `E0030`。** 前者是**运行环境**出问题(内核没给熵、沙箱封了系统调用),后者是程序员把参数写错了。两者的处置完全不同 —— 这与 §11.1 的三分类是同一条线。

**`salt` 收十六进制文本,不是原样字符串。** RFC 8018 / RFC 9106 的 `salt` 是**任意字节串**,而本语言的 `STRING` 是 UTF-8 文本。两个 KDF 的 `salt` 实参**必须**是偶数长度、且全部字符取自 `[0-9a-fA-F]` 的文本,否则产生 `E0030` —— **不**静默截断、**不**猜测。**空串 = 空字节串**是合法的。⇒ **盐的自然来源是 `RANDOM_HEX`**,不是 `RANDOM_BYTES`。

**`ARGON2ID` 没有 `secret`(pepper)/ `assoc`(关联数据)形参。** 曾提议加上,理由是「没有它们就一个 RFC 官方向量都验不了」。

**说明**:唯一的官方向量(RFC 9106 §5.3,带 `Secret[8]` + `Associated data[12]`)在 `RustCrypto/argon2` 0.6.0 上**复现不出来**,而同一 crate 的无 K/X 路径三方一致。一个与其他实现**互不认**的 `secret` / `assoc`,存下来的哈希任何别的实现都验不过 —— 那比没有这个参数更危险。

**两个 KDF 的上下界不是「推荐值」,是硬边界。** 下界取 OWASP 2025 的最小配置(Argon2id `m` = 19 MiB / `t` = 2 / `p` = 1;PBKDF2-SHA256 `c` = 600 000),上界防「一个参数打满机器」。不设下界的话,「参数全显式」等于「调用方能把 `iter` 配成 `1`」—— 那比不给这个成员更危险。

**代价也要写明:越界会拒掉一些合法的历史参数。** RFC 7914 §11 的 `c` = 1 / 80 000 与 RFC 9106 §5.3 的 `m` = 32 KiB **在本成员上都是 `E0030`** —— 它们仍作为**原语层**向量冻结在 `wlwl-std` 的单元测试里。

**`TIMING_SAFE_EQ` 的「长度不泄漏」是规范要求,不是实现细节。** 实现**必须**在两段长度不等时也走完整比较,**不得**提前返回;朴素写法 `a.len() == b.len() && …` 在长度不等时就**提前返回**,于是「两值长度不同」可从耗时上被观察。

**实现注(非规范)** 参考实现的走法是 `max(len)` 步并把长度差折进同一个累加器,函数内没有一处按比较结果分支;该性质由 `wlwl-std` 的机制断言守着。

**诚实边界:耗时仍依赖长度**(比较多少字节就走多少步),这无法避免也不必避免 —— 要隐藏的是「哪几个字节不同」与「是否相等」,不是长度。

### 11.3 三条需要明写的设计取舍

**1. 解码自动识别 base64 字母表。** `BASE64_DECODE` **必须**同时接受 RFC 4648 的标准字母表与 URL 字母表。

**说明**:标准表的 `+/` 与 URL 表的 `-_` 除这两个字符外完全相同,所以「两张都收」是确定性的。Go 的 `StdEncoding.Decode` 会拒 `-`、`URLEncoding.Decode` 会拒 `+`;本成员比它们宽。混用 `+/` 与 `-_` 的串也能解,这是有意的放宽。

**2. `+` 按 RFC 3986 读,不折成空格。** `URL_DECODE` **必须**按 RFC 3986 解释 `+` —— 它是字面加号,**不得**折成空格。

**说明**:`+` → 空格是 `application/x-www-form-urlencoded` 的规则。Go 的 `url.QueryUnescape` 做这个替换,`url.PathUnescape` 不做;本成员对标后者。表单编码请自己处理。

**3. 解码不做有损替换。** 解码成员**不得**对不合法的字节做有损替换;解出的字节不是合法 UTF-8 时**必须**返回 `ERR` 值(`kind` = `"DecodeError"`)。这同时意味着**不能通过 `STRING` 携带任意二进制** —— 要传二进制得先 base64 / hex,再在对面解回 `STRING`。

### 11.4 RFC 测试向量

本节的期望值**全部**取自公开标准或公开检验数据,**不**复制实现输出。向量取自 RFC 4648 §10、RFC 4231 §4 与 FIPS 180-4,第三方**必须**能复现下列每一个期望值。

**base64(RFC 4648 §10)** —— 输入是 ASCII 文本,期望值取自 RFC 4648 §10 的表:

| 输入 | 标准 | URL-safe |
|---|---|---|
| `""` | `""` | `""` |
| `f` | `Zg==` | `Zg==` |
| `fo` | `Zm8=` | `Zm8=` |
| `foo` | `Zm9v` | `Zm9v` |
| `foob` | `Zm9vYg==` | `Zm9vYg==` |
| `fooba` | `Zm9vYmE=` | `Zm9vYmE=` |
| `foobar` | `Zm9vYmFy` | `Zm9vYmFy` |

最后一行的「URL-safe 与标准不同」用 0xFB 0xFF 演示(标准 `+/8=` / URL `-_8=`)—— 但那**不是合法的 UTF-8**,而 wlwl 的 `STRING` 是 UTF-8,所以这个向量只存在于 `wlwl-std` 的 Rust 侧单测,不在语言层可达。语言层能观察到的 URL-safe 分歧用 `U+083F`(UTF-8 字节 `E0 A0 BF`):标准 `4KC/`,URL-safe `4KC_`。

**HMAC-SHA256(RFC 4231 §4)** —— 两个测试用例,密钥与数据都在语言层可表达:

| 测试用例 | 密钥 | 数据 | 期望值 |
|---|---|---|---|
| §4.2 Test Case 1 | 20 个 `0x0B` 字节 | `"Hi There"` | `b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7` |
| §4.3 Test Case 2 | `"Jefe"` | `"what do ya want for nothing?"` | `5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843` |

RFC 4231 的其余测试用例(TC3–TC7)的密钥是**原始字节串**:TC3 / TC6 / TC7 的密钥含非法 UTF-8 字节,TC4 的密钥含裸换行。wlwl 的 `STRING` 是 UTF-8 文本且没有字节转义,这些密钥**无法**以可读文本在语言层逐字表达,因此它们只冻结在原语层。TC1 的密钥是裸控制字节,只能靠粘贴原始字节进入源码 —— 它在本表中按字节列出,是为了让第三方能构造出同一把密钥。

**SHA-256(FIPS 180-4)** —— `SHA256("abc")` 的期望值是 NIST 公布的 SHA-2 检验值:

| 成员调用 | 期望值 |
|---|---|
| `SHA256("abc")` | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` |

**本册参数下的 KDF 期望值** —— 算法取自 RFC 8018 §5.2 与 RFC 9106,参数取本册的下界(OWASP 2025 最小配置)。它们**不是** RFC 的官方向量,但第三方**必须**能复现:

| 成员调用 | 期望值 |
|---|---|
| `PBKDF2_ITER("password", "73616c74", 600000, 32, "sha256")` | `669cfe52482116fda1aa2cbe409b2f56c8e4563752b7a28f6eaab614ee005178` |
| `ARGON2ID("password", "73616c7453616c7453616c74", 2, 19456, 1, 32)` | `7784e9edc034c74be067bacf7f12f6cfb5babfbccd53f7654386c604d40eb808` |

**说明**:两个 RFC 的官方向量在本册的成员层**不可达** —— RFC 9106 §5.3 的 `m` = 32 KiB 与 RFC 7914 §11 的 `c` = 1 / 80 000 都低于本册的下界,调用它们产生 `E0030`。它们仍作为**原语层**向量冻结在 `wlwl-std` 的单元测试里(见 §11.2.1)。

```wlwl
IMPORT("wlwl:std.encode", ["BASE64_ENCODE", "BASE64_DECODE", "SHA256", "HMAC_SHA256"]);
PRINT(BASE64_ENCODE("foobar"));                      // Zm9vYmFy
PRINT(BASE64_DECODE("Zm9vYmFy"));                   // foobar
// U+083F 的 UTF-8 字节是 E0 A0 BF —— 语言层可观察到的 URL-safe 分歧。
PRINT(BASE64_ENCODE("࠿"));                    // 4KC/
PRINT(BASE64_ENCODE("࠿", TRUE));              // 4KC_
PRINT(SHA256("abc"));                                // ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
PRINT(HMAC_SHA256("Jefe", "what do ya want for nothing?"));  // 5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843
```

### 11.5 哈希的边界

本章只提供**单向摘要**:

- **对称 / 非对称加密不做**。标准库给了 AES 就会有人自己攒 TLS —— 误用重灾区。
- **密钥生成不做**。它需要系统随机,与 `std.rand` 的裁决同族(见本节末段)。
- **`MD5` / `SHA-1` 已破,本册不提供**;SHA-3 / BLAKE3 记演进方向。
- **实现不承诺常数时间**;`HMAC_SHA256` 结果的比较**必须**由调用方用 `TIMING_SAFE_EQ` 负责(见 §11.6)。

**有 KDF ≠ 密码学这块齐了。下面三条否决依然成立,且不因 `PBKDF2_ITER` / `ARGON2ID` 的加入而松动。**

- **加解密仍未做,密钥生成仍未做。** 本命名空间现在能安全地处理**口令**(慢哈希 + 参数显式 + 上下界硬),也能生成**不可预测**的随机原料与做**常数时间**比较,但**不能**加密数据、**不能**凭空生成密钥。本节第一条的否决理由原样保留:没有密钥管理就不该给。
- **`algo` 只有 `"sha256"`,不是漏实现。** 签名保留该形参是**留位**(免得日后加值改签名)。SHA-512 若要支持得手写一份实现并另取 FIPS 180-4 向量冻结;而 OWASP 把 PBKDF2-HMAC-SHA-512 的适用场景写成「FIPS-140 合规时」—— 本语言提供不了经 FIPS 校验的实现(没有硬件边界),那条互操作路径不成立。**记为已知限制**,不是设计缺陷。
- **`SHA256` / `HMAC_SHA256` 不是口令哈希。** 它们是**快的**单向摘要:GPU 上每秒几十亿次。口令**必须**走 `PBKDF2_ITER` / `ARGON2ID`。

**实现注(非规范)** 两个 KDF 的本机 release 实测读数:`ARGON2ID`(m = 19 456 KiB / t = 2 / p = 1,OWASP 下界)= **20.3 ms**,`PBKDF2_ITER`(c = 600 000,同为 OWASP 下界)= **833 ms** —— Argon2id 便宜 41 倍,且抗 GPU/ASIC 强得多。读数取自实现仓的基准存档 `impl/crates/wlwl-eval/benches/baseline.txt` 的 KDF 段;**这些是 release 读数,同参数在未优化构建下差 30 到 100 倍。**

**新写的口令存储应当默认 `ARGON2ID`。** `PBKDF2_ITER` 存在的理由是**互操作**:别的系统只能验 PBKDF2 时,它是那条下限,不是「二选一时差一点」。

两边的下界都会让调用方**明显变慢**(0.8 s / 20 ms 量级)—— 这正是 KDF 的意义,但要写进你的超时与 UX 预期里。`ARGON2ID` 每次调用还分配约 19 MiB,别在热路径里逐条哈希。

**`RANDOM_BYTES` / `RANDOM_HEX` 与 `std.rand` 的分工**:要**密钥材料 / 盐 / token** → `std.encode` 的这两个;要**可复现的伪随机序列**(测试用、模拟用)→ `std.rand` 显式播种。**`std.rand` 单向消费** `RANDOM_HEX`,**不得**反向依赖 —— 否则会出现「一个安全一个不安全」的分裂面。

**实现注(非规范)** `ARGON2ID` 引入了 `RustCrypto/argon2` 0.6.0(仓库 `https://github.com/RustCrypto/argon2`,MIT OR Apache-2.0,feature 收窄为 `["alloc"]`);`RANDOM_*` 引 `rust-random/getrandom` 0.3.4(仓库 `https://github.com/rust-random/getrandom`,MIT OR Apache-2.0,`default-features = false` —— 关掉 `sys_rng` 那个**非密码学**的线程局部回退);`PBKDF2_ITER` **手写**(约 30 行,PRF 复用 `HMAC_SHA256` 已有的字节级实现,不引依赖)。实现复用 `wlwl-ast::sha256`(FIPS 180-4 纯 Rust,初为 AST 稳定 ID 而写)—— 单一实现两个消费者,杜绝副本漂移。**不做**对称加密 / 密钥生成 / KDF 便捷封装 / KMS / SHA-3 / BLAKE3 / `MD5` / `SHA-1`。

### 11.6 口令处理的标准写法

**口令的存储必须走慢哈希**(`PBKDF2_ITER` / `ARGON2ID`),**不得**走 `SHA256` / `HMAC_SHA256`。**盐必须每次不同**,**校验必须用 `TIMING_SAFE_EQ`** —— **不得**用 `=`。

下面这段是跑过的(不是示意代码;两条输出在括号里):

```wlwl
IMPORT("wlwl:std.encode", ["RANDOM_HEX", "ARGON2ID", "TIMING_SAFE_EQ"]);

LET(salt, RANDOM_HEX(16));
LET(stored, ARGON2ID("correct horse battery staple", salt, 2, 19456, 1, 32));

// 存库:把 salt 与 stored 一起落盘(盐不是秘密,但必须每次不同)。

// 验签:重新派生一次,再常数时间比较。
PRINT(TIMING_SAFE_EQ(stored, ARGON2ID("correct horse battery staple", salt, 2, 19456, 1, 32)));  // TRUE
PRINT(TIMING_SAFE_EQ(stored, ARGON2ID("wrong horse battery staple", salt, 2, 19456, 1, 32)));      // FALSE
```

三条要点,每条都有代价:

- **盐来自 `RANDOM_HEX(16)`,不是 `RANDOM_BYTES`** —— KDF 的 `salt` 实参收的是**十六进制文本**。盐不保密,但**必须每次不同**(相同盐 ⇒ 相同口令的哈希可直接互相比对,也让彩虹表能一次命中所有人)。
- **参数照抄,不要自己调小**。`2, 19456, 1` 是 OWASP 2025 的下界。想更快就把 `m_cost` 调大(成本随 `m_cost` 线性涨),**不要**把 `t_cost` 调到 1 —— 那正是下界要拦的东西(会被自己的 `E0030` 拒掉)。
- **比较必须用 `TIMING_SAFE_EQ`,不要用 `=`**。朴素比较会在首个不同的字节处提前返回,验签耗时本身就是一条侧信道。

### 11.7 设计依据

**本节为非规范的追溯材料,不构成一致性要求。**

编码族随 v0.11.2 M1 落地;摘要与 KDF 随 v0.11.3 M2 / M6 落地。KDF 的上下界取 OWASP 2025 最小配置;`ARGON2ID` 不收 `secret` / `assoc` 的实测证据见实现仓 `docs/history/addendum-04-crypto-kdf-secrets.md` §3.4。KDF 的性能读数取自实现仓 `impl/crates/wlwl-eval/benches/baseline.txt` 的 KDF 段。
