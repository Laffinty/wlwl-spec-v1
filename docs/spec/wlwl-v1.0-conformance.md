# WLWL 语言规范 v1.0 —— 一致性、稳定性与验证

本册规定这套规范**如何被判定为被遵守**:什么算合规、什么算公共面、哪些变更会破坏兼容性、以及如何验证一个实现确实符合 v1.0。

本册**不定义**语言行为。语言行为在语言核心册、对象与行为类型册、并发册与标准库册。

## 0 导言

### 0.1 本册的构成

本册含七章:第 1 章 一致性定义;第 2 章 条款类型;第 3 章 稳定性政策;第 4 章 公共面;第 5 章 规范与实现的差异登记;第 6 章 验证要求;第 7 章 读者路径与文档层级。

### 0.2 规范性用语

本册中的关键词 **必须**(MUST)、**不得**(MUST NOT)、**应当**(SHOULD)、**可以**(MAY)按以下含义使用:

- **必须 / 不得**:实现的硬性约束。违反时实现必须产生一个诊断(语言核心册 §11)并按 §11.4 终止或报告。
- **应当**:强烈推荐的行为;实现可以偏离,但偏离必须在本规范或实现文档中说明。
- **可以**:真正的实现自由度。

标注为**非规范**(non-normative)的段落、注释与附录不构成一致性要求。

### 0.3 一致性

一个 WLWL 程序是符合本规范的,当且仅当它只使用本规范定义的语法形式与语义,且不依赖任何标注为未定义、保留或实现定义的行为。一个实现是一致的,当且仅当它接受所有一致的程序并产生本规范规定的结果。

本册第 1 章把这一定义拆成可逐条核验的判据。

### 0.4 记法

本册的标点、章节编号与跨册引用约定沿用[总纲 §0.5](wlwl-v1.0-overview.md)。

## 1 一致性定义

### 1.1 程序的合规

一个程序 P 符合本规范,当且仅当同时满足:

1. P 的每个源文件满足语言核心册 §1.1(编码)、§1.2(注释)、§1.3(标识符)、§1.4(关键字)与 §1.10(分号)的要求;
2. P 只使用总纲 §0.6 规范矩阵中**有归属册**的主题所定义的行为;
3. P 不依赖任何标注为**未定义**、**保留**(语言核心册 §12)、**实现定义**或**实现注**的行为;
4. P 在 §2 定义的每一类条款上都满足该类条款的要求。

第 2 条的推论值得写明:**若某个行为在规范矩阵中无归属,它对 P 不构成任何约束**,P 依赖它即不合规 —— 规范的沉默不是许可。

### 1.2 实现的合规

一个实现 I 是一致的,当且仅当:

1. I 接受所有符合 §1.1 的程序;
2. 对每一个符合 §1.1 的程序 P,I 的可观察行为与本规范规定的结果**逐字节一致**;
3. I 对本规范要求的每一个诊断码,在其规定的触发条件下**必然**产生该码,且不产生本规范未定义的码来替代它;
4. I 的可观察行为**不依赖**本规范标注为实现定义或实现注的部分;
5. I 满足第 3 章的稳定性承诺(该条约束的是**发布者**,不是单次运行)。

### 1.3 可观察行为

**可观察行为**是:程序的输出、诊断流、退出码、文件系统与网络副作用、以及通过任务/通道/对象接口对外部可见的状态变化。

**不可观察**的包括:求值顺序在无副作用处的选择、内部表示、诊断的**呈现格式**(码、含义、触发条件、严重级是规范的一部分,排版不是)、以及实现注描述的一切。

§2.1 给出的一条判据在本章反复用到:**被丢弃的值若其丢弃本身可观察,则丢弃是行为;否则不是。** v1.0 的 `E0103`(语言核心册 §8.6)正是靠这条把"丢弃"变成可观察的。

### 1.4 一致性的边界

本规范**不**规定:数值浮点运算的逐位结果(§2.2 只规定 IEEE 754 双精度与舍入模式)、哈希函数的内部实现(标准库册 §11 只规定输出与算法族)、正则引擎的内部结构(标准库册 §16 只规定左最早语义与线性时间承诺)、以及并发调度的具体选择(并发册 §17.8)。

## 2 条款类型

### 2.1 五类条款

本规范每一条陈述属于且仅属于下列五类之一。

| 类型 | 标记方式 | 构成一致性要求 | 允许实现偏离 |
|---|---|---|---|
| **规范条款** | 含有 **必须** / **不得** / **应当** / **可以** | 是 | 仅「应当」类允许,须在实现文档说明 |
| **解释性说明** | 段落以**说明**起首 | 否 | 任意 |
| **实现注** | 段落以**实现注**起首 | 否 | 任意 |
| **示例** | `wlwl` 代码块及其相邻说明 | 否 | 任意 |
| **演进方向** | 路线图册全文 | 否 | 任意 |

**规范条款的判定以关键词为准,不以来源为准。** 一段话若不含四个关键词中的任何一个,就不是规范条款 —— 哪怕它位于正文章节内部。这条规则的代价是:一条真正的硬约束**必须**显式写出关键词,否则不构成约束。

### 2.2 实现注的归位规则

**实现注必须与规范条款物理分离**,具体要求:

1. 实现注只能以**独立段落**出现,**不得**与规范条款同段;
2. 实现注**不得**出现在一条规则的中间 —— 一条规则的规范部分与实现部分之间**必须**有段落边界;
3. 实现注**不得**改变任何规范条款的强度。实现注说"当前实现会……"时,规范条款仍按其字面强度成立;
4. 一段话若同时含有规范断言与实现描述,作者**必须**拆成两段。

违反第 1–3 条的文本是**编辑缺陷**,按一致性册 §6.1 的审查清单处理。

**为什么单列这一条**:v0.11 的规范里,读者无法从措辞判断一句话是"语言保证"还是"当前实现碰巧如此"。这在实现追赶期是便利(不必区分),在 v1.0 冻结期是负债(实现自行偏离,而规范说它不行)。

### 2.3 解释性说明的边界

解释性说明**可以**解释**为什么**有某条规范条款,**不得**成为该条款的前提。判据:删掉整段解释性说明,规范条款是否仍然完整可执行?若是,则该段是解释性说明;若否(条款依赖它才说得通),它**应当**被改写成规范条款。

### 2.4 示例的地位

示例**不**构成要求,但**必须**与它所示范的条款在同一册内,且**必须**在实现上成立。示例与条款冲突时以条款为准,并按 §6.1 记为缺陷。

## 3 稳定性政策

### 3.1 版本号的两条轴

WLWL 有两个独立的版本号,**不得**混为一谈:

| 轴 | 含义 | 递增条件 |
|---|---|---|
| **规范版本** | 本体系的版本,形如 `1.0.0` | 规范文本变更时按 §3.2 |
| **实现版本** | 参考实现的版本,形如 `1.0.0` | 实现变更时按实现仓自身的版本策略 |

**两轴解耦**:实现版本既可能领先规范版本(实现先有新特性,规范后补),也可能落后(规范先定,实现后追)。**规范版本是用户唯一需要跟踪的版本。**

### 3.2 规范版本号规则

规范版本遵循[语义化版本](https://semver.org/lang/zh-CN/)的三段式:

- **主版本**(`1.0.0` → `2.0.0`):出现 §3.4 定义的破坏性变更时递增。
- **次版本**(`1.0.0` → `1.1.0`):新增能力(新章、新成员、新诊断码)且不破坏既有合规程序时递增。
- **修订版本**(`1.0.0` → `1.0.1`):只改措辞、修正笔误、补充解释性说明与示例时递增。

**v1.0 冻结**:自 `1.0.0` 起,规范版本的**主版本**不变。`1.x` 期间只允许:新增能力、新增成员、新增命名空间、措辞修订、以及 §3.4 允许的例外。

### 3.3 公共面

**公共面**(public surface)是本规范下用户**可以依赖**的全部内容,精确清单见第 4 章。公共面**之外**的一切(实现注、示例、路线图册、附录中的非注册镜像)随时可变,不构成兼容性承诺。

### 3.4 破坏性变更

**破坏性变更**是:使某个原先符合本规范的程序不再符合,或使某个原先合规的实现的某项可观察行为不再被规范要求。

`1.x` 期间**不得**出现破坏性变更,**例外仅限**:

1. **安全修复**:修复一个可被外部输入触发的安全缺陷,且没有不破坏合规程序的替代行为;
2. **规范缺陷修复**:修复一处规范内部自相矛盾或与实现事实不符的条款,且该条款的修复方向不引入新的自由度;
3. **勘误**:修正事实性错误(如诊断码含义写反、成员签名写错),且不改变任何可观察行为。

每一次例外**必须**在规范版本的变更记录里写明:受影响的条款号、为什么落在三条例外之内、以及迁移写法。

### 3.5 发布前置条件

一个规范版本**可以**发布,当且仅当:

1. 总纲 §0.9 差异表中的「实现状态」列**没有**「未实现」或「部分」;
2. 第 6 章的验证要求已满足,且验证结果可复现;
3. 公共面(第 4 章)的清单与标准库·注册镜像册附录 A 逐项一致;
4. 一致性册、总纲与被覆盖的各册之间没有悬空的跨册引用。

第 1 条是硬闸门:**规范先于实现发布,等于把一份尚未被任何实现验证过的文本交给用户**。这在 v0.x 期间是可接受的实验姿态,在 v1.0 不是。

下列内容**不**在公共面内:

- 一切**实现注**与**解释性说明**;
- 一切**示例**;
- [路线图册](../roadmap/wlwl-v1.0-roadmap.md)全文;

### 4.3 公共面的冻结点

公共面的冻结点是 **`v1.0.0` 规范发布的那一刻**。冻结之后:

- 新增成员、新增命名空间、新增诊断码:**允许**,次版本递增;
- 修改任一既有成员的签名或可观察语义:**禁止**(§3.4 的三条例外除外);
- 移除或弃用成员:**禁止**;弃用走两步 —— 先发警告码,至少保留一个次版本后再移除,且移除仍属破坏性变更,须走主版本递增。

## 5 规范与实现的差异登记

### 5.1 三态登记

每一条规范条款在实现侧有且只有一种状态:

| 状态 | 含义 | 判定方法 |
|---|---|---|
| **已实现** | 参考实现的可观察行为与条款一致 | 有测试或实测证据 |
| **未实现** | 条款已定,实现侧待办 | 无实现,或有实现但行为不同 |
| **部分** | 行为存在但与条款不完全一致 | 实现有对应路径,但边界情形不符 |

状态登记在总纲 §0.9 的「实现状态」列。**登记是规范的一部分** —— 它不削弱条款的规范性,只陈述实现侧的进度。

### 5.2 登记的纪律

1. 状态**必须**有证据(测试名、实测输出或提交号),**不得**凭印象填写;
2. 「未实现」**不是**「可以不做」。条款自发布起即对实现者构成约束;
3. 规范条款与实测冲突时,**不得**在规范里悄悄改写以迁就实现 —— 走本节登记,再由实现侧收敛。

### 5.3 与上游决策的衔接

规范与实现分离后,实现侧的裁决(ADR、偏差台账)仍然是**实现如何落地规范**的权威,但**不得**反过来成为规范的来源。当二者冲突且无法判定谁对时,按本册 §7.2 的裁决顺序处理。

### 5.4 已登记的规范 ↔ 实现差异

本节登记**规范条款与参考实现当前行为不一致**的项。「规范为准」原则不变:条款的强度不因实现现状而降低;差异在此显式登记,而不是被悄悄写进规范或悄悄留在实现里。

| 编号 | 规范条款 | 规范要求 | 参考实现现状(实测) | 状态 |
|---|---|---|---|---|
| X-01 | 并发册 §17.2.3 / §17.7 | 通道关闭**必须**唤醒其上全部停泊的等待方;被唤醒的发送方**必须**得到 `E0054` | 关闭**不**唤醒停泊的发送方;该任务的 `AWAIT` 得到 `E0053`(无对端唤醒) | 待实现收敛 |
| X-02 | 并发册 §17.3 | `SHIELD` 屏蔽**屏蔽块内收到的**取消请求 | 只推迟**块内 `TASK_CANCEL_PARENT()`** 发起的取消;另一任务 `TASK_CANCEL(handle)` 发起的取消**不被**推迟 | 待实现收敛 |
| X-03 | 语言核心册 §8.6 | 被丢弃的未消费 `ERR` **必须**产生 `E0103` | 未实现:非末条语句的 `ERR` 仍被静默丢弃 | 未实现(总纲 D-01 / D-08) |
| X-04 | 语言核心册 §18.3.1 | 字典键查找 O(1) 期望 | O(n) 最坏 —— 字典的表示是线性扫描的键值序列 | 未实现(总纲 D-02) |

**实测基线**:`Laffinty/wlwl` 提交 `f15051d`,`impl/target/release/wlwl.exe`。核实日期:2026-10-21。

**登记纪律**:本表的「现状」一列**必须**有实测依据(工作负载计数或可复现的观测),**不得**凭印象填写;X-01 / X-02 的复现条件写在并发册 §17.2.3 与 §17.3 的实现注里。

**这些差异不削弱条款**。它们的存在恰恰是「规范即法律」与「规范与实现解耦」两条原则的**可检验标记** —— 一份声称与实现一致的规范,它的差异登记表应当是空的。

## 6 验证要求

### 6.1 文本审查清单

规范文本**应当**在每次发布前通过下列检查。全部检查**必须**可脚本化:

1. **标点契约**:正文无全角 `,` `:` `;` `(` `)`;破折号为 `——`,引号为 `「」`;
2. **跨册引用有效性**:每个 `§N.M` 引用指向确实存在的章节;
3. **诊断码唯一性**:每个码在语言核心册 §11.2 / §11.3 中出现且仅出现一次,无重复登记、无遗漏(标准库册引用的码需在本册有归属);
4. **条款关键词加粗**:`必须` `不得` `应当` `可以` 在规范条款中一律加粗,在解释性说明与实现注中一律不加粗;
5. **实现注分离**:实现注段落独立成段,不含四个关键词;
6. **成员面计数**:标准库·注册镜像册附录 A 的成员数 = 各章成员表逐项之和;
7. **示例有效性**:全部 `wlwl` 代码块在参考实现上运行,结果与相邻注释一致。

第 7 条**必须**真的运行,**不得**以"看起来对"替代。

### 6.2 待验证清单

下列事项**必须**在 v1.0 发布前取得证据,当前状态为**未验证**:

| 项 | 需要验证的命题 | 关联 |
|---|---|---|
| V-01 | §18 承诺的每个复杂度上界,在参考实现上成立 | 语言核心册 §18 |
| V-02 | §19 的资源释放责任,在参考实现上无泄漏 | 语言核心册 §19 |
| V-03 | `E0103` 在 §8.6 列出的每一种丢弃点上都能触发,且不在合法路径上误报 | 语言核心册 §8.6 |
| V-04 | 附录 H 的小步语义与参考实现的实际调度行为一致 | 并发册 附录 H |
| V-05 | 标准库册每一章的失败口径在参考实现上逐条对齐 | 标准库册 §1–§22 |

**未验证**是本册允许的第三种状态(区别于"已实现"与"未实现"):条款已写、性质已明确,但缺少证据。发布前**必须**清零。

### 6.3 上游具名要求

**凡引用外部实现、依赖或上游项目,文档正文必须具名**:项目名、仓库地址、基线提交 SHA、相关 issue 链接。

**为什么**:匿名化让文档丧失可执行性 —— 执行者要多跳一层才能定位代码库,审查者无法核验事实主张,第三方工具可能直接迷路。规范的可信度依赖于"每条事实主张都能被追到源头"。

**规范自身的上游**是实现仓 `Laffinty/wlwl`(基线提交见各册册首的「上游基线」行)。引用它时写全名与提交号,**不得**写"当前实现"。

### 6.4 验证的诚实性要求

验证报告**必须**区分三类结论:**已核实**(附原始输出)、**待验证**、**已裁决**。把"没报错"写成"检查通过"是本规范体系最严重的缺陷类型 —— 它把绿灯当成证据。

**阴性对照**是必需的:任何"检查器报告 0 问题"的结论,**必须**附带一次**故意注入已知故障**的运行,证明该检查器确实有能力抓到它。

### 6.5 检查器

本仓库自带两个脚本,把 §6.1 的检查项变成可重复的门禁:

| 脚本 | 作用 |
|---|---|
| `script/check_spec.py` | 执行 §6.1 的七项检查,分「错误」与「提示」两级输出。退出码 0 = 无错误 |
| `script/negctl.py` | **阴性对照**:向规范文本的副本注入已知故障,验证检查器确实能抓到 |

```
python script/check_spec.py --impl <参考实现的 wlwl 可执行文件>
python script/negctl.py --impl <参考实现的 wlwl 可执行文件>
```

`--impl` 省略时,第 7 项(示例有效性)被跳过并报为「已跳过」—— **不得**把跳过的绿灯当作通过。

**检查器自身的可信度**由 `negctl.py` 保证:它注入四类故障(全角标点、指向不存在章节的引用、指向不存在文件的链接、跑不通的示例块),要求检查器**逐条报错**。阴性对照不通过,检查器的绿灯不成立。

**编号空间的处理**:语言三册共用一套编号(§1–§19),标准库各册共用另一套(§1–§22)。检查器按此解析引用;跨册引用缺册名时报「提示」。

**已实现的两项专项检查**:

| 检查 | 判据 |
|---|---|
| **诊断码归属与唯一性** | 诊断码表的归属是语言核心册 §11.2 / §11.3。同一码被定义两次 → 错误;**别的**册在表格首格位置定义了一个码 → 错误。正文里**引用**一个码不算定义(只认表格首格)。 |
| **成员面双向对拍** | 注册镜像册的每个命名空间,其成员集合**必须**等于对应标准库册成员表的成员集合。两侧都成稿时不一致 → 错误;只有一侧成稿 → 提示。 |

## 7 读者路径与文档层级

### 7.1 四条最短阅读路径

| 读者 | 路径 |
|---|---|
| 第一次写 WLWL 程序 | 语言核心册 §1–§8 → 标准库册对应章 → 一致性册 §1 |
| 实现一个解释器 | 总纲 §0.6、§0.7 → 一致性册全文 → 语言核心册 §1–§9、§11、附录 A → 并发册 §17 |
| 实现一个标准库成员 | 标准库册对应章 → 语言核心册 §2、§8、§11 → 一致性册 §3、§4 |
| 审计一份实现 | 一致性册 §1.2、§6 → 总纲 §0.9 → 各册 §11.2 与标准库册各章的「失败」列 |

### 7.2 冲突裁决顺序

当两处文档给出不同说法时,按下列顺序取信:

1. **总纲 §0.6 规范矩阵**决定谁有管辖权;
2. 有管辖权的那一册说了算;
3. 若同册内两处冲突,取**更具体**的一处(章 > 节 > 段);
4. 若仍无法判定,该问题**是规范缺陷**,按 §6.1 记为缺陷并修规范 —— **不得**由实现侧自行择一。

第 4 条是关键:规范内部的矛盾**必须**在规范里解决,不能推给实现。

### 7.3 文档层级

总纲 §0.8 定义了四层(L-规范 / L-实现注 / L-决策 / L-历史)及其变更节奏。本册补充两条:

1. **L-实现注的硬规则**:它永远**不得**成为可观察行为的第二来源。它与 L-规范冲突时改它;它与源码实测冲突时改它;只有走完裁决并登记,才允许动 L-规范。
2. **L-实现的引用必须带核实日期与提交号**,形如 `> 最后核实:2026-10-21 · commit <sha>`。没有核实标记的机制描述**一律视为可疑**,用到就重新核。

### 7.4 变更本体系

- 规范文本的变更走本册第 3 章的版本规则;
- 每次变更**必须**更新总纲 §0.9 的差异表;
- 新增册**必须**同步更新总纲 §0.1 的册表与 §0.6 的规范矩阵 —— 册表与矩阵不一致即为缺陷。
