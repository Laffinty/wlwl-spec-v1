# WLWL 语言核心规范 v1.0

本册定义 WLWL 语言的**核心**:词法、类型与值、绑定与作用域、表达式、函数、控制流、模式匹配、错误模型、模块与程序、标准库机制面、诊断、复杂度保证与内存模型。

- **一切都是表达式**。没有语句与表达式的二分;每个构造求值后产生一个值。
- **一切运算皆调用**。没有中缀运算符;算术、比较、逻辑都是具名函数,按 `name(arg, ...)` 前缀形式调用。
- **默认不可变**。绑定一旦建立即指向固定值;容器操作返回新容器而非修改原容器;状态突变只能经由 `LET MUT` 显式声明的单元格进行(对象字段的突变规则见对象册 §13.4)。
- **错误即值**。可恢复错误是 `RESULT` 值,沿调用链透明传播,由显式的消费者函数处理(§8)。

对象模型、行为类型与 `THIS` 见[对象与行为类型册](wlwl-v1.0-objects.md);并发见[并发册](wlwl-v1.0-concurrency.md);标准库成员契约见[标准库册](../stdlib/)。

> 核实日期:2026-10-21。核实方法与要求见[一致性册 §6.3](wlwl-v1.0-conformance.md)。

### 0.3 规范性用语

本册中的关键词 **必须**(MUST)、**不得**(MUST NOT)、**应当**(SHOULD)、**可以**(MAY)按以下含义使用:

- **必须 / 不得**:实现的硬性约束。违反时实现必须产生一个诊断(§11)并按 §11.4 终止或报告。
- **应当**:强烈推荐的行为;实现可以偏离,但偏离必须在本册或实现文档中说明。
- **可以**:真正的实现自由度。

标注为**非规范**(non-normative)的段落、注释与附录不构成一致性要求。

### 0.4 一致性

一个 WLWL 程序是符合本规范的,当且仅当它只使用本册与其它规范册定义的语法形式与语义,且不依赖任何标注为未定义、保留或实现定义的行为。一个实现是一致的,当且仅当它接受所有一致的程序并产生本规范规定的结果。完整判据见[一致性册 §1](wlwl-v1.0-conformance.md)。

## 1 词法结构

### 1.1 源文件

一个 WLWL 源文件是一个 **必须** 为 UTF-8 编码(带或不带 BOM)的字节序列。换行**可以**是 `\n`、`\r\n` 或 `\r`,三者等价。源文件是一个模块(§9)。

**说明**:三种换行在词法上等价,故同一份源码在任何平台上的词法结果相同。

旁路签名文件 `.wll.sig`(§9.6)的编码要求**本版不规定**,按实现定义处理 —— 它是语言设施而非工具选择,这一空白**应当**在下一次规范修订前补上。清单文件 `wlwl.toml` 与锁文件 `wlwl.lock` 属包管理器职责,不在本册范围内(§9.4)。

### 1.2 注释

- `//` 开始一个**行注释**,延伸到行尾。
- `/*` 与 `*/` 界定一个**块注释**。块注释**必须**正确嵌套。
- `///` 开始一个**文档注释**,延伸到行尾。文档注释只在词法上与行注释相区别,**不得**影响程序语义。

注释中出现的任何字符序列(除上述定界规则外)都是注释的一部分。

### 1.3 标识符

```
identifier = letter { letter | decimal_digit | "_" } .
```

`letter` 含 Unicode 字母类别(含中文)。标识符区分大小写。非 ASCII 标识符是合法的;工具**应当**在诊断中如实回显。

以 `_` 单独出现的标识符是**通配符**,见 §3.1 与 §7.2。

### 1.4 关键字

```
TRUE    FALSE   NULL    LET     FUN     RETURN
IF      WHILE   FOR     BREAK   CONTINUE
CLASS   NEW     THIS    NOT
```

关键字**不得**用作标识符。`CLASS`、`NEW`、`THIS` 的语义见对象册 §13 与 §15:它们出现在调用形式 `CLASS(...)`、`NEW(...)`、`THIS()`(或零参引用 `THIS`)中,分别构造类、实例化对象、引用当前实例。

`MUT` 是**上下文关键字**:仅在 `LET` 之后的位置具有特殊含义(§3.1);其他位置可作普通标识符使用,不与关键字冲突。

**`SEALED` 不是关键字**(§9.1)。它以**前缀调用 / 模块头声明**形式书写,与 `CLASS(...)` / `NEW(...)` 同形,因此本节的关键词表不含 `SEALED`,§12 的保留集合相应为空。

### 1.5 运算符记号

以下记号是内建运算函数名,可用前缀调用形式书写(§4.3、§4.6):

```
+   -   *   /   %   ==  =   !=  <   >   <=  >=  &&  ||  !
```

`=` 的角色由**文法位置**唯一决定:

1. 出现在 `OpToken` 位置(`=` 后紧跟 `(`)→ 相等函数调用 `=(a, b)`,与 `==` 同义(注册表 `Eq => "=="` desugar,见 §4.3)。
2. 出现在 `Postfix` 形式的 `=` 位置(`... [ Expression ] "=" Expression`)→ `INDEX_SET` 语法糖(见 §4.5)。
3. 出现在形参表 `Param` 内(`name = Expression`)→ 默认值分隔符(见 §5.2)。

三者互不重叠,无需词法前瞻。

`=` 与 `==` 在调用位置同义(都指相等函数);`!` 与 `NOT` 关键字(§1.4)同义,两种形式均无警告。

### 1.6 整数字面量

```
int_lit        = decimal_digit { decimal_digit } .
int_literal   = [ "+" | "-" ] int_lit .
```

整数值是有符号 64 位整数。运算结果超出该范围的规则见 §2.2。

**实现注(非规范)**:前导符号字面量 `+x` / `-x` 在语法分析阶段被改写为 `+(0, x)` / `-(0, x)`,与二元运算同路径;`NEG` 是独立的 1 元内建,只能按名调用。可观察行为与「前导符号字面量」等价:同 `INTEGER` 下界、同 §2.2 溢出语义。

### 1.7 浮点字面量

```
float_lit      = digits "." digits | digits exponent | digits "." digits exponent .
exponent       = ( "e" | "E" ) [ "+" | "-" ] digits .
```

浮点值是 IEEE 754 双精度数。整数与浮点字面量统称**数字字面量**。

### 1.8 字符串字面量

```
string_lit     = '"' { string_element | interpolation } '"' .
string_element = any_char_except_quote_backslash_newline_dollar | escape .
interpolation  = "${" Expression "}" .
escape         = "\" ( "n" | "t" | "r" | "\" | '"' | "/" | "0" | "b" | "f" | "$" ) .
```

字符串是 Unicode 码点的不可变序列。承认的转义:`\n` 换行、`\t` 水平制表、`\r` 回车、`\\` 反斜杠、`\"` 引号、`\/` 斜杠、`\0` 空、`\b` 退格、`\f` 换页、`\$` 字面 `$`。其他转义**不得**出现(`E0001` 或 `E0002`)。

**字符串插值**:`"Hello, ${name}!"` 中 `${...}` 内的表达式按完整表达式语法求值;求值结果以 `STR`(§10.3)渲染后嵌入字符串;求值若产生 `ERR` 则按 §8.2 透传,整个字符串字面量表达式的结果为该 `ERR`。

### 1.9 布尔与空字面量

`TRUE`、`FALSE` 产生布尔值;`NULL` 产生空值。

### 1.10 分号

处于"语句位置"的表达式**必须**以 `;` 结束。在括号序列(§4.4)内部,最后一个表达式的 `;` **可以**省略;该表达式的值即括号序列的值。省略必需的 `;` 产生 `E0013`。

## 2 类型与值

### 2.1 值域

WLWL 是动态类型语言:类型属于值而非名字。值的论域由以下**类型**构成:

| 类型 | 含义 |
|------|------|
| `NULL` | 空值,唯一成员 `NULL` |
| `BOOLEAN` | `TRUE` 或 `FALSE` |
| `INTEGER` | 有符号 64 位整数 |
| `FLOAT` | IEEE 754 双精度浮点数 |
| `STRING` | Unicode 码点的不可变序列 |
| `ARRAY` | 值的不可变有序序列 |
| `DICT` | 从键(STRING、INTEGER 或 INSTANCE)到值的插入序映射,不可变 |
| `FUNCTION` | 闭包(§5.4) |
| `RESULT` | `OK(v)` 或 `ERR(e)` 变体(§8) |
| `TASK` | 任务句柄;`SPAWN` / `TASK_CURRENT` 返回(并发册 §17.1) |
| `CHANNEL` | 通道句柄;`CHANNEL_NEW` 返回(并发册 §17.2) |
| `CLASS` | 类对象;`CLASS` 构造器返回(对象册 §13.2) |
| `INSTANCE` | 类实例;`NEW` 返回(对象册 §13.3) |

数组与字典字面量见 §4.8;`TYPE(x)` 返回上表名称的字符串(`RESULT` 两个变体都报 `"RESULT"`)。

类型名(`NULL`/`BOOLEAN`/`INTEGER`/`FLOAT`/`STRING`/`ARRAY`/`DICT`/`FUNCTION`/`RESULT`/`TASK`/`CHANNEL`/`CLASS`/`INSTANCE`)是 `TYPE` 返回的字符串,**不**构成标识符绑定。命名空间成员**可以**与类型名同名(如官方包 `agent` 的 `TASK`),二者在各自作用域中独立解析。`TYPE` 的参数位置不做名字解析 —— 它取运行时值,返回字符串,过程中不查任何名字表。

`TYPE` 对句柄报 `"TASK"` / `"CHANNEL"`,对类对象报 `"CLASS"`,对实例报 `"INSTANCE"`。句柄的真值按 §2.3「其余一切值为真」;相等按 §2.4;显示形态见 §2.5。

**键的约束**:字典的键**必须**是 `STRING`、`INTEGER` 或 `INSTANCE`。`INSTANCE` 作键按**对象身份**判定(§2.4):同一实例命中,异实例不命中。其它类型作键**类型不符**,产生 `E0031`。NaN(§2.2)**不得**作键(`E0031`)。

### 2.2 算术性质

- 整数运算按二进制补码语义进行;`+`、`-`、`*` 溢出时**抛错** `E0035`(`INTEGER` 与 `FLOAT` 越界共用此码)。`NEG` 于 `INTEGER` 下界取负产生 `E0034`。
- `/(a, b)` 当两操作数为整数时是**截断除法**(商向零取整):`/(7, 2)` 为 `3`,`/(-7, 2)` 为 `-3`。两操作数为浮点时是浮点除法,可产生 `Inf`/`NaN`。
- `b` 为零时 `/(a, b)` 产生 `E1003`(整数、浮点皆然,即使 IEEE 754 允许 `Inf`)。
- `%(a, b)` 只接受整数:`a - /(a, b) * b`,符号与被除数一致;`b` 为零产生 `E1003`。任一实参是 `FLOAT` 时产生 `E0030`(类型错)。

**说明**:整数溢出抛错而非回绕,是本语言"失败可见"原则(§2.2、§8)在算术层的体现。

### 2.3 真值

**假值**恰为八个:`FALSE`、`NULL`、`0`、`0.0`、`""`、空数组、空字典、`NaN`。**其余一切值为真**,包括非空数字、非空字符串、非空容器、`OK(FALSE)` 之类的 `RESULT` 值、以及 `CLASS` / `INSTANCE` 值。

真值仅由 §6.1 的 `IF`、§6.2 的 `WHILE`、`&&`、`||`、`NOT`、`BOOL` 以及模式匹配以外的谓词位置消费。

### 2.4 相等

`==(a, b)`(别名 `=`,§1.5)与 `!=(a, b)`:

- 数字跨类型比较:`==(1, 1.0)` 为 `TRUE`。
- 字符串按码点逐位比较;布尔、空按恒等。
- 数组按长度与逐元素深度相等;字典按键集与逐键值深度相等(受上一条 NaN 规则影响:含 NaN 的容器与任何值都不等)。
- 函数按闭包实例引用相等。
- `RESULT`:`OK(a) = OK(b)` 当且仅当 `a = b`;`ERR(e1) = ERR(e2)` 当且仅当 `e1 = e2`;`OK` 与 `ERR` 永不相等。
- 任一操作数为 `ERR` 变体时,比较函数**不**求布尔,而是透明传播该 `ERR`(§8.2)。
- `TASK` / `CHANNEL` 句柄按句柄身份恒等:同一句柄与自身相等,不同句柄不相等。
- `CLASS` / `INSTANCE` 按**对象身份**恒等:同一类对象与自身相等,两次 `CLASS(...)` 调用产生的类对象不相等,即使成员相同;同一实例与其别名相等,两次 `NEW(...)` 产生的实例不相等,即使字段值相同。该规则比照句柄的身份相等,不改变上列既有类型规则。

### 2.5 显示

`PRINT`(§10.2)与 `STR`(§10.3)将值渲染为文本:布尔为 `TRUE`/`FALSE`,空为 `NULL`,数组为 `[e1, e2, ...]`,字典为 `[k: v, ...]`,函数为 `<fun(params)>`。`STR` 对字符串恒等;对浮点保留小数表示(整数产生的浮点显示一位小数,如 `2.0`)。

句柄显示为 `<task handle id=N gen=M>` / `<channel handle id=N gen=M>`。

类对象显示为 `<class Name>`(匿名类为 `<class>`);实例显示为 `<Name instance>[N fields]`(匿名类实例为 `<instance>[N fields]`),其中 `N` 为实例字段个数。显示形态仅供诊断,**不得**作为程序判等或解析依据。

### 2.6 静态类型词汇(编译期)

本节描述的是**注解词汇**,不是运行期值域。§2.1 的表才是值的论域;`TYPE(x)`(§2.5)**永不**返回本节的名字。这些名字只出现在类型注解(§5.2)与旁路签名文件(§9.6)里,**且仅当 `[features] gradual_typing` 开启时才被解释**(§5.2.1)。

| 注解类型 | 含义 |
|---|---|
| `INTEGER` / `FLOAT` / `STRING` / `BOOLEAN` / `NULL` | 与 §2.1 同名运行期类型的顶层形状 |
| `ARRAY[T]` / `DICT[K, V]` | 容器;`T` / `K` / `V` 为类型参数 |
| `OPTION[T]` | **纯注解糖**:§2.1 没有这个运行期类型。它的两个见证是 `NULL`("就是没有")与 `RESULT[T, ·]`("或者是一个 T",错误侧不要求已知)。**裸 `T` 不满足 `OPTION[T]`** —— 否则 `OPTION` 退化成 `T` 的别名,失去全部意义 |
| `RESULT[T, E]` | `OK(_)` / `ERR(_)` 两个构造子 |
| `FUN[...] -> U` | 函数类型。**箭头形式不在语法内**(见本节末) |
| `DYNAMIC` | 未标注处的回退类型;它与任何类型双向可赋值,因此**从不**产生诊断 |
| `T: Bound` | 类型变量(§5.2.1) |

`TASK` / `CHANNEL` / `CLASS` / `INSTANCE`(§2.1)在本层**不做结构化建模**,作为不透明具名类型参与比较。

**三条规范性事实**:

1. **容器类型用方括号,不用尖括号。** `ARRAY` **要求**方括号,裸写 `ARRAY` 报 `E0010: expected '[' after 'ARRAY' in type expression`。`DICT` / `OPTION` / `RESULT` 裸写**不报语法错**,映射成带 `DYNAMIC` 参数的正式变体(`DICT[DYNAMIC, DYNAMIC]` / `OPTION[DYNAMIC]` / `RESULT[DYNAMIC, DYNAMIC]`),不是「不透明具名类型」。
2. **尖括号形式与箭头形式的命运不同。**
   - `DICT<STRING, INTEGER>` 是**响亮的语法错**:`E0011: expected ')', got Gt`。
   - `FUN(INTEGER) -> STRING` 才是**静默吸收**:词法层没有 `->` 终结符(`-` 与 `>` 是两个独立记号),残余记号被并进类型名,得到 `FUN ( INTEGER ) - > STRING` 这个谁也不认识的类型 —— 用户看不到任何错误,却也得不到任何检查。**本规范不承认这两种形式**。
   - 单个类型参数的 `DICT<STRING>` 同样被静默吸收成 `DICT < STRING >`。
3. **显式约束只跟在裸标识符后,且不可嵌套。** `T: Comparable` 合法;`ARRAY[INTEGER]: Comparable` 报 **`E0010`**,消息是 `a type constraint may only follow a bare type variable`(与返回类型失配的 `E0112` 无关)。约束**不可右嵌套**:`T: Comparable: Integer` 报 `E0010: a type constraint may not be nested`。给**已知基类型**加约束是无意义的废话,约束被丢弃、类型不变:`INTEGER: Comparable` 就是 `INTEGER`。吸收不可达的类型形式时,残余记号会被并进类型名并**保留整个类型头**,所以格式化器能把这样的源码原样写回、可再解析。

## 3 变量、作用域与单元格

### 3.1 绑定

`LET(name, value)` 在**当前作用域**为 `name` 建立一个**不可变绑定**,并将 `value` 存入新创建的**单元格**(cell)。`LET` 表达式本身的值是 `NULL`。

`LET MUT(name, value)` 建立**可变绑定**:单元格的可变标志在创建时即置为真,允许后续 `SET`(§3.4)改写。

```wlwl
LET(x, 1);              // 不可变
LET MUT(count, 0);      // 可变
```

`LET` 的第一个实参**可以**是解构模式,此时按模式同时建立多个绑定;模式**必须**与值精确匹配,失配产生 `E0026`:

```wlwl
LET([a, b], [1, 2]);            // a=1, b=2
LET([head, *rest], [1, 2, 3]);  // head=1, rest=[2, 3]
LET(["k": v], ["k": 9]);        // v=9
LET([_, x, _], [1, 2, 3]);      // x=2
```

模式形态的完整定义见 §7.2。`LET MUT` 仅接受简单标识符,不支持解构。

**通配符模式**:`LET(_, value)` 的模式是通配符,**不**建立任何绑定,`value` 仍按完整表达式求值。该形式是本语言**唯一的显式丢弃构造** —— 它对 §8.6 的未消费 `ERR` 规则有专门语义(§8.6.4)。

**说明**:通配符模式与 `LET` 的普通形态在求值上无差别,差别只在**是否留下一个可读的绑定**。§8.6 之所以把"留下可读绑定"当作语义事件,是因为只有可读的绑定才能被消费。

### 3.2 作用域与遮蔽

作用域由**函数体、括号序列(§4.4)、`FOR` 循环体、`MATCH` 分支体**引入,以及每个模块的顶层。作用域按词法嵌套。

- 内层作用域中的 `LET` **总是**在内层新建单元格;若外层已有同名绑定,内层绑定**遮蔽**外层。
- 同一作用域中对同一名字再次 `LET` 是**重绑定**:旧绑定被替换。
- 读一个不存在的名字产生 `E0020`(附最近候选名)。
- **没有**变量提升:在 `LET` 之前读名字产生 `E0020`。

### 3.3 单元格可变性

每个绑定由一个单元格实现,单元格持有值与一个可变标志。可变标志由绑定形式决定:`LET` 建立的为不可变,`LET MUT` 建立的为可变。该标志一经设定**不再改变**。

当一个闭包捕获某单元格时,捕获环境保留对该单元格的引用;不论该单元格是 `LET` 还是 `LET MUT` 所建立,闭包均按原标志判定是否可写。多个闭包可共享同一单元格。

```wlwl
LET(make_counter, FUN((),
    (LET MUT(count, 0);
     FUN((), (SET(count, +(count, 1)); count)))
));
LET(c, make_counter());
c();   // 1
c();   // 2 — count 的单元格在闭包间共享
```

这是 WLWL 中唯一的原位状态突变机制(对象字段的突变是第二条显式路径,见对象册 §13.4)。循环累加等命令式惯用法**应当**经由 `LET MUT` 与 `SET` 表达,或 `REDUCE`(标准库册 §5)。

### 3.4 SET

`SET(name, value)` 将 `name` 当前绑定的单元格改写为 `value`:

- 名字不存在 → `E0020`。
- 单元格不可变(由 `LET` 建立而非 `LET MUT`)→ `E0024`。
- `SET` 表达式的值是 `NULL`。

`SET` 对不可变单元格产生 `E0024`,不论该写入发生在单任务内还是跨任务(并发册 §17.1)的共享单元格上;跨任务与单任务路径统一,不存在独立的跨任务错误码。

**说明**:`SET` 改写单元格时,旧值的处置受 §8.6 约束 —— 旧值若是一个未被消费的 `ERR`,改写即构成一个丢弃点。

### 3.5 遮蔽内建

`LET` 或命名函数定义(§5.1)遮蔽第 10 章的内建名时:默认产生 `E0025`;当模块清单声明 `[features] allow_builtin_shadow = true` 时允许并产生警告 `W0030`。遮蔽保留关键字(§1.4)产生 `W0030`。

## 18 复杂度与性能保证

### 18.1 记法

- `n` —— 被操作容器的元素个数;对字符串是码点数,对字典是键数。
- `m` —— 第二个操作数的规模(字符串拼接时是另一段的长度)。
- **最坏** —— 该操作在所有合法输入上的代价上界。
- **摊还** —— 一串同类操作的**总**代价除以操作数所得的界;单次操作**可以**超出该界。
- **期望** —— 对实现内部的随机化取期望;单次操作**可以**超出该界。

复杂度只计**语言可观察的**代价:函数调用、容器构造与元素访问。实现内部的内存分配、回收、缓存局部性**不**计入。

### 18.2 承诺强度

| 档 | 含义 | 约束力 |
|---|---|---|
| **规范性上界** | 实现**必须**在该界内完成该操作 | 构成一致性要求 |
| **推荐上界** | 实现**应当**在该界内完成;偏离**必须**在实现文档中说明 | 弱约束 |
| **实现定义** | 规范**不**给界;实现**必须**在文档中声明自己的口径 | 无上界,但须声明 |
| **仅注记** | 记录当前实现的实测行为 | 无约束 |

**规范性上界是"必须满足",不是"当前已达到"。** 某一操作当前未达标的,在 §18.6 登记为已知偏差并附收敛路线;条款的强度**不**因实现进度而降低。

### 18.3 核心容器的操作上界

| 操作 | 上界 | 档 | 说明 |
|---|---|---|---|
| `LEN(arr)` / `LEN(d)` | O(1) | 规范性 | |
| `arr[i]`(下标读) | O(1) | 规范性 | |
| `d[k]`(键读) | O(1) 期望 | 规范性 | §18.3.1 |
| `HAS(d, k)` | O(1) 期望 | 规范性 | |
| `INDEX_SET(d, k, v)`(键已存在) | O(1) 期望 | 规范性 | |
| `INDEX_SET(d, k, v)`(新键) | O(1) 摊还 | 规范性 | 键序是插入序,新键追加到末尾 |
| `PUSH(arr, x)` | O(n) 最坏 | 规范性 | 数组不可变,必须产出新数组 |
| `CONCAT(s, t)` | O(n+m) 最坏 | 规范性 | |
| `SLICE(arr, i, j)` | O(n) 最坏 | 规范性 | 产出新数组 |
| `==(a, b)`(数组 / 字典) | O(n) 最坏 | 规范性 | 深度相等(§2.4) |
| `SORT(arr)` 的比较器调用次数 | O(n²) 最坏 | 规范性 | §18.5.1 |

#### 18.3.1 字典查找的期望复杂度与插入序

字典的**键序是插入序**,这一点是可观察的(§2.1、§2.5:JSON 渲染、错误载荷、任务结果都依赖它)。O(1) 期望的键查找与插入序**不冲突**:实现可以在内部维护一张哈希索引指向位置,对外仍按插入序呈现。

键的哈希由实现内部决定,**不**要求与 `STR` 渲染一致;实现**不得**因为哈希而改变可观察的键序。

#### 18.3.2 数组追加的代价结构

`PUSH` 返回**新**数组,原数组不变(§3.3、§10.4)。因此单次 `PUSH` 的代价**必须**是 O(n) 最坏 —— 产出 n+1 个元素的新数组,拷贝量下界是 Ω(n)。

**这不意味着"建一个 n 元数组要 O(n²)"。** 后者取决于**惯用法**:若每次追加都把上一个结果当作输入重新产出,则总代价是 O(n²);若实现能识别"同一个累加器被反复追加"这一形态并就地累积,则总代价可以是 O(n) 摊还。§18.4 对这两种形态分别给出承诺。

### 18.4 高成本惯用法与推荐写法

| 惯用法 | 目标代价 | 档 | 说明 |
|---|---|---|---|
| 循环内 `SET(acc, PUSH(acc, x))` 累积 n 个元素 | O(n) 摊还 | 推荐上界 | 见 §18.4.1 |
| 循环内 `SET(acc, CONCAT(acc, t))` 累积字符串 | O(n) 摊还 | 推荐上界 | 同上 |
| 循环内逐次 `INDEX_SET(d, k, v)` 写 n 个键 | O(n) 摊还 | 推荐上界 | §18.3.1 的哈希索引让单次插入 O(1) |
| 单次 `PUSH` / `CONCAT` | O(n) / O(n+m) | 规范性 | §18.3 |

#### 18.4.1 累加器形态

"同一个绑定在循环体内被反复追加"是本语言最常见的建容器写法。实现**应当**识别该形态并避免每次重拷整个容器;**可以**选择不识别(则该惯用法退化为 O(n²),但**必须**在实现文档中说明)。

**判断该形态的推荐写法**:把累加器声明为 `LET MUT` 绑定,循环体内**只**对它做 `SET(acc, PUSH(acc, x))` 一种写法的追加。`PUSH` / `CONCAT` / `+` 三种追加形态**都**出现在真实代码里,只认一种会让另外两种静默退回平方级。

#### 18.4.2 更省事的替代

能用标准库成员一次算完的,**应当**用它,而不是手工累加:`MAP` / `FILTER` / `REDUCE` / `FOLD_RIGHT` / `SORT_BY` 等单遍成员比手工循环更快也更清楚(成员契约见标准库册 §5)。

### 18.5 明确不承诺的性能

| 项 | 口径 |
|---|---|
| 常数因子 | **不**承诺。同一操作在不同实现上的常数差异**不**构成不一致 |
| 延迟 / 吞吐 | **不**承诺任何数值阈值 |
| 内存占用 | **不**承诺。值的大小、分配的次数、是否存在回收都属实现自由度(§19.5) |
| `SORT` 的 O(n log n) | **不**承诺,理由见 §18.5.1 |
| 并发路径的吞吐 | **不**承诺。并发路径**只**保证正确性与无泄漏 |
| 回收停顿 | **不**承诺。若实现使用回收机制,其停顿**不**构成不一致 |

#### 18.5.1 为什么 `SORT` 不承诺 O(n log n)

比较排序的 O(n log n) 上界要求比较器给出**全序**。本语言的 `SORT` 口径是"不可比 ⇒ 判相等"(标准库册 §5.1),这给出的是**偏序** —— 偏序上的排序结果**未指定**,且不存在能同时满足"稳定"与"组间次序确定"的全序。

因此 `SORT` 的比较器调用次数上界是 **O(n²) 最坏**。实现**可以**做到更少(若它能在偏序上做拓扑排序),但**不得**承诺 O(n log n)。

#### 18.5.2 复杂度判定的口径

**复杂度的判定不使用墙钟比值。** 同一份线性实现在不同机器上可能测出 4 倍与 12.8 倍的差异,比值里混着缓存命中率与调度噪声,不足以判定复杂度。

判定必须用**确定性工作量计数**(比较器调用次数、元素访问次数、拷贝的元素个数),并满足两条:① 带**下界断言**,确认计量点确实被走到;② 计量点收在**被测数据结构内部** —— 在调用点计数对"内部换成线性扫"不敏感。

### 18.6 与参考实现的关系

本节登记**当前参考实现未达到** §18.3 规范性上界的项,以及各自的收敛路线。上游基线见册首的「上游基线」行。

| 项 | 规范上界 | 参考实现现状 | 收敛路线 |
|---|---|---|---|
| `d[k]` / `HAS` / `INDEX_SET`(语言级) | O(1) 期望 | O(n) 最坏 —— 字典的表示是线性扫描的键值序列,每次查找逐项深比较 | 需要内部哈希索引 + 插入序物化;该表示变更**本批未做**,须另立决策 |
| 循环内累加数组 / 字符串 | O(n) 摊还(推荐上界) | 数组 O(n²);字符串超线性 | 可变累加器形态识别已实现,覆盖 `PUSH` / `CONCAT` / `+` 三种追加形态 |
| `SORT` 比较次数 | O(n²) 最坏 | 恰好 C(n,2) 次 | **不追求** O(n log n) —— §18.5.1 已说明原因 |
| `MAP` / `FILTER` / `CHUNK` / `WINDOW` 等建数组族 | O(n) 摊还 | 已达标(单遍内核) | —— |

**偏差登记的纪律**:上表的"现状"一列**必须**有实测依据(工作负载计数或基准存档),**不得**凭印象填写;收敛路线**必须**指向一份已裁决的决策或一条明确的待办,**不得**只写"以后优化"。

## 19 内存与资源模型

### 19.1 值与生存期

WLWL 的值是**不可变**的。值的生存期由**绑定**决定,不由值本身决定 —— 一个值可以被任意多个绑定持有,也可以不被任何绑定持有。

值的**可观察行为**不含"它住在哪儿":两个内容相等的值在一切可观察的方面等价(§2.4、§2.5)。

**规范不暴露任何内存管理原语。** 没有 `FREE`、没有 `DELETE`、没有引用计数查询、没有显式所有权转移。程序员**无法**观察到内存管理的存在。

### 19.2 单元格与别名

每个绑定由一个**单元格**实现(§3.1、§3.3)。单元格**按引用**共享:

- 闭包捕获某单元格时,捕获环境保留对该单元格的引用(§3.3);
- 同一单元格可被多个闭包、多个作用域、多个任务同时持有;
- 单元格的可变标志在创建时设定,**不再改变**(§3.3)。

**别名不引入悬垂**:单元格的生存期由持有它的绑定与闭包共同决定,与它被引用的次数无关。

**别名 + 可变**是本语言唯一的共享可变状态。它**不**提供任何同步保证(对象册 §16.3);并发册 §17.0.1 把"共享可变状态"列为本语言的反模式。

### 19.3 容器与共享

容器(数组、字典)不可变(§2.1)。因此**共享容器是安全的**:不存在"两个持有者看到不同内容"的可能。

但**元素**仍适用 §19.2 的别名规则 —— 一个元素可以是某个单元格的值的拷贝,也可以是共享的实例(§2.1 允许 `INSTANCE` 作字典键)。

### 19.4 资源的释放责任

| 项 | 规范要求 |
|---|---|
| 通用 | 资源在**取得它的操作返回后**必须仍然可用,直到该操作或该资源类型规定的释放点 |
| 任务 | 任务终止时其资源释放;`SCOPE` 结束时该作用域内的任务**必须**全部已终止(并发册 §17.1) |
| 通道 | 通道在其最后一个持有者消失时释放;`CHANNEL_CLOSE` 提供显式关闭(并发册 §17.2) |
| 文件 / 进程 / 网络 | 释放责任由**各成员自己**规定,见标准库册对应章;本册**不**统一规定 |

**程序终止时,全部资源必须被释放**:进程退出、文件描述符关闭、网络连接关闭、子进程被收割。实现**不得**因为某个失败路径而泄漏资源。

**规范不要求显式关闭 API**,除 `CHANNEL_CLOSE` 外。

### 19.5 内存管理策略

规范**不**规定实现采用何种内存管理策略。实现**可以**使用垃圾回收、引用计数、区域分配、所有权转移或它们的组合。

实现**必须**保证:

1. **无悬垂**:任何按引用共享的对象(§19.2)在所有持有者消失前保持有效;
2. **无泄漏**:程序终止时全部资源被释放(§19.4);
3. **不因策略改变可观察行为**:内存管理**不得**改变值相等(§2.4)、键序(§18.3.1)、显示(§2.5)或任何诊断。

实现**不得**把内存管理策略暴露为可观察行为 —— 程序**无法**区分"值被回收了"与"值还在"(§19.1)。

### 19.6 与对象模型的关系

类对象与实例按引用共享(对象册 §13.2、§13.3)。实例字段的写入对所有持有该实例的引用可见(对象册 §16.3)。

这是 §19.2 别名规则在对象模型上的延伸:**共享 + 可变**,同样不提供同步保证。
