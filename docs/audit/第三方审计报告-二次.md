# WLWL v1.0 规范体系二次审计报告

## 一、 总体评价：从“爱好者实验”到“工业级规范”的跨越

经过对 `Laffinty/wlwl-spec-v1` 仓库的 11 册规范体系（总纲、语言核心、对象、并发、一致性、标准库 5 册及注册镜像册）的深度审阅，本审计委员会得出结论：**WLWL v1.0 规范体系已经达到了极高的工程化与形式化水准，完全具备作为严肃编程语言标准的资格。**

与 v0.11 版本相比，v1.0 体系不仅在内容上进行了扩充，更在**规范治理架构**上实现了质的飞跃。引入的“规范矩阵（Normative Matrix）”、“条款类型物理分离”、“独立一致性册”以及“机器验证与阴性对照（negctl）”机制，标志着该项目已经脱离了“代码即文档”的早期草莽阶段，进入了“规范即法律（Spec as Law）”的成熟期。这种将规范与实现解耦、并通过差异登记表（§5.4）诚实面对实现债务的做法，正是 Rust、WebAssembly 等顶级工业语言演进的标准范式。

## 二、 对首轮审计意见的复核与确认

在首轮审计中，我们指出了 wlwl 在工程化文档、形式化语义和性能约束方面的短板。v1.0 体系对这些意见进行了极具深度的审视与处置，本审计对作者的裁决表示**高度认同**：

### 1. 关于“模块别名”与“Continuation”的反驳（完全成立）
*   **模块别名**：作者指出 `IMPORT(path, ["orig": "alias"])` 已解决命名冲突，且 wlwl 摒弃了 `ns.MEMBER` 的命名空间限定调用语法，因此传统意义上的“模块别名”缺乏生存土壤。**审计确认**：这一裁决深刻契合 wlwl “一切皆前缀函数调用”的极简哲学，强行引入 `import as` 反而会破坏语法的一致性。
*   **Continuation (续体)**：作者明确 wlwl 的并发模型是“代数效果（Algebraic Effects）+ 协作式挂起”，恢复点位于挂起点**之后**，而非传统的 CPS 续体捕获。**审计确认**：在并发册附录 H 中引入小步操作语义（Small-step Semantics）来形式化 Yield/ChannelOp，比引入沉重的 Continuation 概念更精准、更符合当前单线程调度器的实现事实。

### 2. 关于“未消费 ERR 静默丢弃”的修复（重大里程碑）
v1.0 引入了 `D-01` 变更：**未消费的 `ERR` 不再静默丢弃，产生 `E0103`，并提供 `LET(_, expr)` 作为唯一显式丢弃构造。**
**审计确认**：这是 v1.0 最具价值的语义修正。它彻底堵死了 v0.11 中“早期错误被静默吞没”的致命漏洞，使 wlwl 的错误处理模型达到了 Go/Rust 级别的严谨性，确保了程序行为的完全可预测性。

### 3. 关于“性能语义”与“稳定性政策”的落地（完美采纳）
*   **性能语义**：作者将复杂度上界（如字典 O(1)、数组追加 O(n)）正式升格为**规范性条款**（语言核心册 §18），并诚实登记了当前实现（O(n) 线性扫描）与规范的差异（X-04）。
*   **稳定性政策**：独立成册的《一致性册》明确定义了 SemVer 规则、公共面（Public Surface）以及破坏性变更的三条例外。
**审计确认**：这完全满足了首轮审计的要求，为 v1.0 的长期演进奠定了法理基础。

## 三、 v1.0 发布前的“最后一公里”阻碍（差异清零审查）

根据《一致性册》§3.5 的发布前置条件：“总纲 §0.9 差异表中的「实现状态」列**没有**「未实现」或「部分」”。然而，当前 §5.4 仍登记了若干差异。要在 v1.0 冻结前达到发布标准，必须对以下差异进行**产品裁决**：

### 1. API 分叉问题（X-05）
*   **现状**：全局内建 `INPUT(prompt?)` 支持可选提示，而 `std.io::INPUT` 只收 0 个实参。
*   **审计建议**：这是典型的 API 设计缺陷。规范**必须**统一两者的签名。建议将 `std.io::INPUT` 的签名修改为 `INPUT(prompt?) -> STRING`，以保持标准库与全局内建的语义同构。此修改属于“勘误/缺陷修复”，不违反稳定性政策。

### 2. 性能契约的妥协与坚持（X-04）
*   **现状**：规范承诺字典查找 O(1)，但实现为 O(n)。
*   **审计建议**：若 v1.0 发布时底层哈希表实现无法就绪，**不得**带着“未实现”状态发布。建议将语言核心册 §18 的规范措辞暂时降级为：“字典键查找**应当**提供 O(1) 期望复杂度，当前参考实现为 O(n) 最坏情况”。待后续实现优化后，再通过次版本（v1.1）将“应当”收紧为“必须”。

### 3. ERR 令牌的底层语义漏洞（X-06 / X-07）
*   **现状**：当容器内嵌套多个未消费 `ERR`，或 `ERR` 经由标准库回调（如 `MAP`）返回时，由于实现侧采用“每绑定一个布尔令牌”的机制，导致部分 `ERR` 丢失（假阴性），无法触发 `E0103`。
*   **审计建议**：这暴露了 §19（内存与资源模型）中对“ERR 传播令牌”的形式化定义不足。规范不能仅停留在“被丢弃即报错”的表面语义，必须在 §19 中补充**令牌的传递与合并语义**（例如：当多个 ERR 汇入同一容器时，是保留第一个、最后一个，还是聚合为列表？）。若实现侧短期内无法支持多令牌追踪，规范需明确界定 `E0103` 的**触发边界**（例如：“仅在标量绑定与直接语句值丢弃时保证触发”），以避免规范与实现的长期撕裂。

## 四、 深度优化建议（面向 v1.0 冻结及未来演进）

尽管 v1.0 体系已极其完备，但为了应对未来的生态扩张，建议在以下微观层面进行最后打磨：

### 1. 强化“阴性对照（Negative Control）”的覆盖面
当前 `negctl.py` 注入了 4 类故障（标点、引用、链接、示例）。建议增加**语义级阴性对照**：
*   故意在规范中写入一条“与 §8.2 透明传播相悖”的假规则，验证检查器是否能通过交叉引用发现逻辑冲突。
*   故意在标准库册中遗漏一个 `E0xxx` 诊断码的归属，验证“诊断码唯一性”检查是否能精准拦截。

### 2. 标准库“资源释放责任”的闭环验证
系统册（§1, §2, §15 等）引入了“资源释放责任”小节。建议在《一致性册》§6.2 的待验证清单中，明确要求提供**基于 Valgrind 或 Rust Miri 的内存/句柄泄漏测试报告**，作为 v1.0 发布的硬性证据，确保“无泄漏”不仅仅是文本承诺。

### 3. 官方包（AI/Agent）的“桩（Mock）”形态声明
在标准库·官方包册中，`CALL_TOOL` 等成员当前返回“桩回包”。建议在规范中引入 **`[stub]` 标签**，明确规定：“带有 `[stub]` 标签的成员，其返回值形状**不**构成公共面契约，实现侧可在不递增主版本号的情况下替换为真实实现”。这为 AI 功能的快速迭代留出了合法的规范空间。

## 五、 最终结论

**WLWL v1.0 规范体系已经成功完成了从“代码附属品”到“独立法律实体”的蜕变。**

其首创的**规范矩阵**与**条款物理分离**原则，为动态类型语言的规范化提供了极具参考价值的范本。当前存在的 X 系列差异，并非规范的失败，而是“规范先行”策略下必然经历的阵痛。

**发布建议**：
1.  **立即执行**：修复 X-05（API 分叉），统一 `INPUT` 签名。
2.  **裁决执行**：针对 X-04（字典复杂度）和 X-06/07（ERR 令牌），选择“修改规范以匹配实现（降级承诺）”或“推迟 v1.0 发布直至实现收敛”。**绝不可带着“未实现”的硬伤发布 v1.0.0**。
3.  **冻结发布**：一旦上述差异清零，v1.0 体系即可正式冻结（Freeze），并以此为基础启动 wlwl 本体的 v1.0 对齐工程。

wlwl 已经证明，即使是爱好者驱动的项目，凭借极致的工程自觉与形式化追求，同样能构建出比肩顶级工业语言的规范体系。期待 v1.0 的正式发布。
