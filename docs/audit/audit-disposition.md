## 2 三条不成立意见的核验细节

这三条是本次审计中**若照单全收会把规范改坏**的条目,核验过程与证据在此留档。

### 2.1 模块别名(意见 5)

**审计原文**:"在所提供的材料中,完全没有关于此功能的任何定义。"

**核验**:语言册 §9.2 的 `IMPORT` 文法含 `name_array`,其元素形态为 `["orig": "alias"]`,原文:"`["orig": "alias"]` 将导出名 `orig` 绑定为本地名 `alias`(重命名)"。

**为什么这是误读**:审计要的是 `use path as p` 形态的**模块级**别名。但 WLWL 的文法里不存在命名空间限定调用 —— 语言册 §10.6 原文:"**「全限定写法」在本语言不存在**:文法没有「命名空间限定调用」表达式,冒号只出现在 `IMPORT` 的路径字符串与改名处。"

⇒ 在这门语言里,"模块别名"没有对应的概念空间。引入它需要先引入限定调用,属语法级重设计。

### 2.2 延续传递机制(意见 6)

**审计原文**:"'Continuation'一词仅在标题中出现,其定义和用法完全为空白。"

**核验**:语言册 §17.0.1 有明确条文,原文含"本规范**没有**续体保存"、"挂起只是「让出控制再回来」,回来之后从挂起点**之后**继续,而不是从挂起点**之内**继续";§17.4 另有代数效果执行模型。

**为什么这是误读**:审计的前提(定义空白)与事实相反。审计的**担忧**(并发模型的可预测性依赖底层语义)成立,但正确的应对是**形式化现有语义**,而不是补一套不存在的语义 —— 后者会让 v1.0 首次对实现说谎。

### 2.3 稳定性政策与 R0–R2(意见 3、4)

**核验**:标准库册 §0.7 给出 R0/R1/R2 三层定义、四条机械归属判定规则、层间规则与归属总表;§0.8 给出 v0.x 与"1.0 起"两段稳定性政策与"四件套"同步要求。

**残余问题**:这两处都在**标准库册**里,语言册无对应条款,且没有一处言明 R0/R1/R2 与规范层级的关系。⇒ v1.0 的动作是**升格与澄清**,不是**从零补写**。

## 3 意见 7 的核验与设计(唯一的行为变更)

意见 7 是本次审计中**唯一要求改变语言行为**的意见,因此核验与设计都做到底。

### 3.1 v0.11 现状(实测)

实测基线:实现仓 `f15051d` 的 release 二进制 `impl/target/release/wlwl.exe`。

| 源码 | 实际行为 | 退出码 |
|---|---|---|
| `PRINT("a"); ERR("x"); PRINT("b");` | 打印 `a`、`b`;`ERR` **静默丢弃**,无任何诊断 | 0 |
| `LET(r, ERR("x")); PRINT("ok");` | 打印 `ok`;`ERR` 进单元格,不外泄 | 0 |
| `PRINT("a"); ERR("x");`(末条) | `E0102` 顶层逃逸 | 1 |
| `LET(_, ERR("x")); PRINT("ok");` | 打印 `ok`;**不传播、不报错** | 0 |
| `LET(f, FUN((), ERR("x"))); PRINT("a"); f(); PRINT("b");` | 打印 `a`、`b`;函数返回的 `ERR` **静默丢弃** | 0 |
| `LET(r, ERR("x")); r; PRINT("b");` | 打印 `b`;读出但未消费的 `ERR` **静默丢弃** | 0 |

⇒ §8.5 的表格是准确的,缺陷真实存在:**失败可以在程序的任意位置被无声吞掉**。

### 3.2 v1.0 规则的设计约束

设计时受三条事实约束,每条都经实测或源码核实:

1. **逃生舱必须零新增表面语法。** 实测确认 `LET(_, expr)` 可用:解析器把 `LET(_, …)` 记为通配符模式(实现仓 `wlwl-parser/src/lib.rs:935`),求值器对通配符不建立绑定(`wlwl-eval/src/lib.rs:9511`),且实参**确实被求值**(实测 `LET(_, PRINT("side"))` 打印 `side`)。⇒ `LET(_, expr)` 就是现成的"显式丢弃"构造,不需要新增 `IGNORE()` 之类的内建。
2. **"已被消费"不能挂在值上。** `Value` 是 `#[derive(Clone)]` 的普通枚举,数组与字典按值深拷贝(`wlwl-value/src/lib.rs:117`)。若把"已消费"标记挂在值上,`LET(a, err); LET(b, a);` 之后消费 `b` 不会清掉 `a` 的副本 ⇒ 误报。⇒ 标记必须挂在**绑定(cell)**上,绑定不被别名共享。
3. **诊断码必须有确定的位置。** 语言册 §11.2 的码位占用情况为:`E0100` PANIC、`E0101` 栈溢出、`E0102` 顶层逃逸、`E1003` 除零;`E0103` **未被占用** ⇒ 新码定为 `E0103`,与 `E0102` 同族。

### 3.3 规则的形状(细节见语言核心册 §8.6)

- **未消费** = 该 `ERR` 尚未被**取走型**消费者取走(`ERR_PAYLOAD` / `UNWRAP_OR` / `TRY` / `UNWRAP` / `WRAP` / `EXPECT_ERR`),且未被显式丢弃,且未传播到顶层被报告;
- **观察型**消费者(`IS_ERR` / `IS_OK` / `BOOL` / `TYPE` / `==` / `!=`)**不**取走 —— 与语言册 §8.3 表格"返回布尔,不消耗载荷"的既有表述一致;
- **丢弃点**三处:语句值丢弃、绑定被覆盖、作用域结束时仍未消费;每处**必须**产生 `E0103`;
- **转发**:绑定被读取时错误状态随之转移 —— 读入取走型消费者则视为已消费,读入其它位置则由接收方承担。⇒ `LET(a, err); LET(b, a); ERR_PAYLOAD(b);` **不**误报;
- **每个 `ERR` 只报告一次**:报告后视为已处理,避免同一次错误在丢弃点与作用域结束各报一次;
- 末条语句的 `ERR` 成为程序值,仍走 `E0102`(§8.5),不走 `E0103`。

### 3.4 已知代价(如实登记)

这条规则是 v1.0 里**影响面最大的破坏性变更**:v0.11 依赖"非末条语句静默丢弃"的程序会开始报 `E0103`。实现仓当前的探针与契约用例中,凡把 `ERR` 放在非末条语句位置的,都需要改写。

已在总纲 §0.9 以 `D-01` / `D-05` / `D-08` 三条登记,实现状态为「未实现」,并写进一致性册 §3.5 的发布前置条件。

### 3.5 审计意见未被采纳的部分

审计原话:"把「未消费 `ERR` 即为无消费者」变成可判定规则,需要先定义「哪些构造算消费」。"

v1.0 **没有**走这条路。理由:那要求先枚举"消费"的构造,枚举不全会漏(漏掉一个 = 仍有静默丢弃的口子),枚举过宽则误报。v1.0 改用**丢弃点**建模 —— 只在**错误确实消失**的地方报告,不依赖"什么算消费"的完备枚举。取走型/观察型的二分只是消费构造的分类,不承载完整性。

## 4 对审计方法本身的记录

审计基于三册规范文本与公开资料,**未读实现源码**。这个方法决定了它能发现什么、不能发现什么:

- **能发现的**:规范文本自身的缺口(内存模型、复杂度、规范矩阵、稳定性政策的位置错配)与行文层面的结构问题。这四类发现**全部成立**,是本次 v1.0 的主要输入。
- **不能发现的**:规范文本**已经定义**但审计误以为缺失的内容(模块改名、续体语义、R0–R2、稳定性政策)。这类误判源于**只读文本、不做交叉核验**。
- **不产生断言的**:实现与规范是否一致。审计明确声明"本报告重点在于识别并剖析规范文本本身存在的不足",这个自限是对的 —— 但它意味着审计结论**不能**直接当作"实现有缺陷"的证据。

⇒ 对规范体系本身的一条教训:**任何对规范文本的外部审计,结论在进入 v1.0 之前必须逐条对照原文核验**。这与本仓既有的第三方功能性审计规程一致(那一轮是"黑盒、不读源码"、期望值手写自规范);本轮是**白盒、只读文本**,两者的核验方式不同,但"期望值不得抄自被测对象"这条纪律同样适用。
